# 自写测试 vs 隐藏测试覆盖率审计 — 汇总

来源：`coverage/sheet.md`（100 条隐藏意图逐条核对）、`coverage/github.md`（100 条）。方法见两份文件开头。

## 1. 三档计数

| | full | partial | none | skip(unknown) | 合计 |
|---|---|---|---|---|---|
| Sheet | 43 | 30 | 24 | 3 | 100 |
| GitHub | 63 | 22 | 12 | 3 | 100 |

去掉 skip 后可评估：Sheet 97 条、GitHub 97 条。full 命中率：Sheet 44%（43/97）、GitHub 65%（63/97）——与开头背景给出的隐藏测试实际通过率（Sheet ~80/100、GitHub ~23/100）方向不完全对应：Sheet 的"自写测试真正覆盖到关键断言"的比例比隐藏测试通过率低得多，说明 Sheet 隐藏测试里有相当一部分即使自写测试没有针对性覆盖、应用也可能碰巧做对了；反过来 GitHub 自写测试覆盖率（65% full）明显高于隐藏测试实际通过率（约23%），说明 GitHub 这边"测了但应用没做对"或"测的和真实隐藏测试要求的实现细节有出入"的比例更高——self-written 测试覆盖率不是隐藏测试通过率的可靠代理指标，两题的失配方向还不一样。

## 2. 漏测类型归类（partial + none 共 88 行，标签可多选，故下表条数之和大于 88）

| 类别 | 条数 | 含义 |
|---|---|---|
| DUP_ONE_VARIANT 多种同类情况只测一种 | 22 | 需求/意图列了多个并列子情形，自写测试只挑其中一个 |
| OTHER 其他遗漏 | 21 | 断言缺了意图点名的某个具体细节，不属于以下任何一类 |
| CROSS_FEATURE 跨功能交互未测 | 12 | 两个需求点组合使用的场景（如排序后筛选是否仍生效）完全没人测 |
| BOUNDARY 边界值/极端输入未测 | 11 | 需求给出的边界值、空字段、越界输入被绕开 |
| ISOLATION 多实体隔离未测 | 9 | 多工作簿/多工作表/多仓库/多组织互不影响没有验证 |
| PERSIST 持久化缺刷新/重开验证 | 9 | "刷新后保持"类意图没有真正刷新，或刷新的不是该场景要保持的那个对象 |
| PERMISSION 权限拒绝路径未测或测反 | 7 | 无权限用户应被拒绝/看不到入口的场景未测，或测试者用了有权限身份 |
| REJECT_STATE 拒绝路径完全未触发 | 6 | 需求已给出专用的失败种子（重复名、空值等），自写测试从未提交过这次失败操作 |

**DUP_ONE_VARIANT 示例**：
1. Sheet REQ-5-1-1 #2/#6：排序功能的 6 条自写测试数据全是文本和数字，从未出现日期值，需求点名的"ISO 日期降序排序"两条隐藏意图完全没有测试触及。
2. GitHub REQ-1-3 #2：修改密码的自写测试只构造了"当前密码错误"一种拒绝原因，需求同时要求测试的"确认密码不一致"分支从未被测过。

**OTHER 示例**：
1. GitHub REQ-4-2-1 #1：提交历史查看测试只断言了 commit message 文本和相对时间，隐藏意图明确要求同时看到"消息、作者和时间"三项，作者字段从未被断言。
2. GitHub REQ-3-2-3 #1/#2：复制 HTTPS/SSH 克隆地址的测试只验证界面上出现 "Copied" 提示文字，从未真正读取浏览器剪贴板的实际内容来确认复制的确实是合法可粘贴的 URL 或 SSH 地址格式。

**CROSS_FEATURE 示例**：
1. Sheet REQ-5-1-1 #4：排序后此前已生效的筛选条件是否继续正确控制可见行，全组 6 条排序测试没有一条在排序前创建过筛选。
2. Sheet REQ-2-2-1 #4：插入行后，引用了被移动单元格的公式是否正确调整引用，5 条插入/删除行测试没有一条包含公式。

**BOUNDARY 示例**：
1. Sheet REQ-5-2-1 #2：数值范围校验规则反复验证了"越界值被拒绝"，但从未提交过边界值本身（如恰好等于上限/下限）来确认边界值会被正常接受。
2. Sheet REQ-3-1-2（粘贴二维表格）5 条测试固定复用同一份无空字段的 2×2 数据，"保留空字段""保留矩形外数据"这两个需求点名的场景因为测试数据里根本没有可验证的空字段或哨兵数据而无法证实。

**ISOLATION 示例**：
1. Sheet REQ-1-1-1 #2：从首页打开指定工作簿是否会带入其他工作簿的数据——两条相关自写测试自始至终只操作唯一一个种子工作簿 Q3 Sales，从未打开第二个工作簿做交叉对比。
2. Sheet REQ-3-2-2 #7：撤销操作是否跨工作簿隔离，全部撤销/重做测试都只在单一新建工作簿内操作，没有测试验证撤销一个工作簿不会影响另一个同时打开的工作簿。

**PERSIST 示例**：
1. GitHub REQ-6-2-1 #2：隐藏意图要求"应用 Open 筛选后刷新，筛选结果仍保持"，自写测试却是先直接刷新默认（未筛选）列表页，从未先套用筛选再刷新。
2. GitHub REQ-3-1 #4：隐藏意图要"刷新搜索结果列表页本身"，但全部 4 条搜索测试的刷新动作都发生在点开某个仓库详情页之后，测的是仓库详情持久化而不是搜索结果列表持久化。

**PERMISSION 示例**：
1. GitHub REQ-3-4 #2：隐藏意图是"无管理员权限的用户看不到可见性修改入口"，自写测试却是用仓库所有者本人登录，断言"能看到 Change visibility 按钮"——测的是相反的结论，不是漏测而是测反了。
2. GitHub REQ-6-1 #2 / REQ-4-3-3 #2：分支保护规则和修改默认分支的"非管理员应被拒绝"场景，自写测试作者留下注释"没有已知凭据的非 Admin 账号"后直接用 test.skip() 跳过，整条测试从未运行过。

**REJECT_STATE 示例**：
1. GitHub REQ-3-2-1 #2/#3：需求原文明确给出了"默认命名空间下已存在同名仓库"这个专用种子用来测重复名拒绝，三条创建仓库的自写测试全部使用随机唯一名，一次都没用上这个种子；空仓库名同理完全没试过。
2. GitHub REQ-2-2-3 #2：成员重复添加/未知账户两种拒绝场景对应的自写测试是空的 test.skip()，全组没有一条测试真正提交过这两种失败输入。

## 3. 自写测试的系统性偏差

1. 同需求内的场景互相高度雷同，测试预算没有花在刀刃上。最典型的是 Sheet 排序（6 条测试全用文本/数字，0 条用日期）、GitHub REQ-3-1 搜索（4 条测试里 3 条只是签入状态和搜索词的细微变体）、GitHub REQ-3-2-2 Fork（第二条测试完整重复第一条，只是换个随机名）。同一操作反复换无关紧要的参数，比真正扩展覆盖面更常见。
2. "刷新后保持"被机械化成 page.reload() 加复核最外层标题/可见性，而不是复核该场景真正要保持的具体内容（筛选状态、diff 内容、透视数值、搜索结果列表本身）。这是自写测试互测分数虚高、但对着真实隐藏意图逐条核对后大量掉到 partial 的最主要原因——动作看起来对，断言的深度不够。
3. 遇到"不知道具体怎么构造"的场景时，倾向于彻底回避而不是尝试。需求文本里已经明确给出的负面种子（重复仓库名、越界数值、非法分支名、空标题）系统性地不被使用；需要额外角色/账号的权限场景，要么直接 test.skip() 并注释"没有对应账号"放弃，要么退而求其次测一个总能通过的良性检查。
4. 权限类负面场景是最不可靠的一类，且存在"测反"这种比单纯漏测更危险的失败模式：GitHub REQ-3-4 #2 用仓库所有者本人的身份断言"能看到"可见性修改按钮，实际验证的结论和隐藏意图"非管理员看不到"完全相反——如果不逐条核对隐藏意图、只看这条自写测试"通过"，会得出完全错误的安全结论。
5. 跨功能交互（CROSS_FEATURE）几乎全部集中在 Sheet：Sheet 的各原子需求天然共享同一张工作表（排序、筛选、公式、数据校验、透视表互相耦合），但自写测试把每个需求当成互不相干的孤岛来测，排序×筛选、排序×公式、插入行列×公式/校验、透视×筛选/结构变化，五组常见组合全部或几乎全部零覆盖。GitHub 由于功能边界本身更清晰（不同页面/不同资源），这类交互缺口相对少。
6. "复杂新功能"比"看似简单的老功能"测得更认真：Sheet 透视表（9 条里 6 条 full）远好于排序（6 条里 0 条 full）；这与直觉相反，但符合"写测试的模型对看起来复杂、需要更多步骤搭建的功能反而更谨慎，对看起来一步到位的功能反而抄需求文本最基本的一句话就收工"的合理解释。

## 4. 方法与过程说明（供复核）

- 逐条判定采用与 oracle/BRIEF.md 一致的方法论：在同一顶层需求（REQ-N）文件组的全部自写测试里找最佳匹配，不限同编号 #k；持久化意图要求真实刷新（page.reload()）或重开（回首页重新进入）后断言；拒绝类意图要求断言状态未变。
- 执行方式：按顶层需求分组并行核对（Sheet REQ-2/3/4/5、GitHub REQ-1/2/4/6 由子审计分别完成，Sheet REQ-1、GitHub REQ-3 由本层直接核对），最后统一汇总复核。
- 过程中出现了严重的多 agent 协作事故：多个子审计在处理过程中收到或自称收到相互矛盾的"最终汇总权"指令，一度并发覆盖 coverage/ 下的共享文件，并各自产出了未经交叉核对的全量重跑结果。这些未经验证的版本已全部弃用；本文件及 sheet.md/github.md 是基于逐组独立结果、经过至少两处人工交叉核对修正（GitHub REQ-3 的 n1/n4 两条根据独立复核收紧了判定）后的版本，任何早于本次写入的磁盘内容均不代表最终结论。
