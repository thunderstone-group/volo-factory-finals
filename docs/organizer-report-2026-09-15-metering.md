主办方好，反馈一个计量归因的问题，附数据。

**现象**：今天 10:14–10:15 我们（VOLO AI）在 arc-bench-web 上同时开了 7 个 run（两份 submission，分别跑 5 个和 2 个任务，平台允许并发，全部同时 RUNNING）。它们结束后，平台给每个 run 记的 token 和费用几乎相同，而且都等于整个账户在这段时间的总用量：

| run | 任务 | 平台记的 token | 平台记的费用 |
|---|---|---:|---:|
| 332541babb5d / b0ff49104419 / abb087c9b2ad / a9696c7ee767 | stackoverflow / prestashop / 12306 / ctrip | 30,124,871（四个 run 完全相同） | CNY 37.663134（完全相同） |
| f079898ea278 | bookstack | 30,050,676 | CNY 37.190881 |
| d130ad13f228 / 2c8302b9bef9 | keep / bookstack（ARC 模板） | 29,910,448（两个相同） | CNY 36.452976（相同） |

meter.arc-bench.com 上同一账户 UTC 02:00–04:00 两个小时的用量合计正好是 **30,124,871 token、CNY 37.66**——和上面四个 run 各自被记的数一模一样。也就是说 7 个 run 加起来被记了 CNY 260.75，实际只花了 CNY 37.66，同一笔用量被记了七遍。运行日志里对应的行是 `[backend] Meter usage captured: tokens=29910448, cost=36.452976 CNY`。

**机制判断**：平台给 run 记账用的是「run 开始/结束时读账户计量表，取差值」，而不是每个 run 自己的请求用量。只要同一把 access key 上有任何并行流量（另一个官方 run、或选手本地调试打同一把 key），差值就会把别人的用量算进来。昨天我们 Ticket 赛道的 run 也出现过 50 万 token 的他人缓存命中被算进来（E057）。

**影响**：
1. 榜单的费用列和 cost efficiency（senior 层的排名依据）在任何并发情况下都不可信；并发是平台允许的，选手很难避免。
2. 反过来也会漏记：如果一个 run 的窗口里别的 run 恰好结束并抵消，或选手在 run 期间没有任何流量，数字倒是准的——所以现在榜上「谁便宜」取决于谁碰巧串行。
3. 我们这 7 个 run 的费用列请按实际处理或作废；如果平台按这些数扣额度，我们账户被多扣了约 CNY 223（余额已到 −1.35，网关从 10:48 起返回 402 insufficient_balance，7 个 run 的生成阶段全部因此中断，这也是它们通过率很低的原因）。

**建议**（任一即可）：
- 给每个 run 单独发一把子 key（或让 runner 注入 `X-Run-Id` 之类的头），meter 按 key/run 归因；
- 或者 meter 保留每条请求记录（目前 `/api/user/requests` 已经有请求级明细），平台按 run 的时间窗和 key 之外再加 run 标识过滤；
- 短期：服务端把同一账户的 run 串行排队，并在文档里写明「并发会污染费用列」。
