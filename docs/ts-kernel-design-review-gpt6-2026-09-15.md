## 2. “模型不写自检”的反面

**【已核实】模型仍然在写检查，只是输出从 JavaScript 换成了 Check JSON。** 选择准备路径、输入、定位名称和断言，仍然都是模型判断。Schema 能限制格式，不能保证 THEN 被正确理解。

**【推断】没有哪条官方行为在原理上“只能由模型写代码检查”。** 足够完整的解释器都能覆盖。但当前九种 Step 覆盖不了截图变化、排序、数量差、日期状态等；要么扩充解释器，要么保留受限的自定义检查出口。

我的替代是：

- 通用、已校准的检查由 harness 执行并冻结。
- 特殊行为允许模型编写**有预算、一次性的诊断 probe**，不自动加入回归集，也不赋予验收权。
- 产品修复不能顺手修改验收检查。

**【已核实】官方 ARC 的做法也不是单纯翻译三个关键词。** TestGenerator 位于接口设计之后，输入包含接口 schema、场景、上下文和设计产物，并区分 Unit、Integration、E2E。它要求检查真实状态转换，并另有检查修复阶段。[官方 TestGenerator](~/projects/arcbench-campaign/upstream/platform-templates-2026-09-15/arc/agents/context/prompts/test_generator.py:19)。

### 费用推演

**【已核实：历史用量的截断算术】** 将 R=8 理解为一次 implement 加最多八次调用，每批只保留原轨迹前九个响应，按请求实际模型价格重算：

- 第 7 局：已开始的 12 批及 contract 合计约 **¥7.38**。

## 4. §3.2：JSON store 的容量不是主要风险，状态契约才是

### Express + JSON 文件够不够

**【推断】对这一级数据规模，可以够；没有证据需要为了 135 条测试立即换数据库。** 26 个用户不是吞吐量指标。单进程内存状态、同步完成的行级修改、串行落盘及临时文件 rename，足以作为两天方案。

但必须满足：

- 会话按浏览器客户端隔离，不能把 currentUser 放进全局 store。
- 更新按实体／字段执行，不能让客户端读全库后再整库覆盖。
- 订单、乘客、账户修改具备明确的提交边界。
- 健康检查成功代表种子和关联已准备好。

**【已核实】已有第 7 局运行时已经包含 JSON store、原子文件替换、启动种子和 health gate。** 这些能力不依赖 Express 重写才获得。[现有 state.cjs](~/projects/volo-factory/runs/2026-09-15-keep-full-7/app/backend/state.cjs:15)。

**【推断】1 核／2 GiB 下，四个浏览器 worker 比这几十条账户数据更值得担心。** 既有 12306 的 135/135 是本机 hosted 配置回放，不能证明相同资源限制下的性能。最终需要相同 CPU、内存和并发配置的验收。

### §3.1 的种子保证不成立

**【已核实】`reconcile` 不会机械补出完整 SeedRow。** 它只要在整个 seeds JSON 中找到一句声明的**任意一个引号值**，就认为该句已覆盖。例如，已有账户包含公共密码 `Password123!`，缺失另一用户身份的声明仍可能被略过。本轮用内存中的合成反例确认了这一点。[contract.py](~/projects/volo-factory-worktrees/ts-kernel/volo/contract.py:379)。

**【推断】把这个函数原样移植，再将 seeder 设为只读，会把漏账户、错归属、漏关联固化到整个生成过程。** 12306 的用户还关联乘客、订单；保存引号字符串不等于建立这些关系。

替代方案是验证每条声明的主体身份、必要字段和关系引用；未解决的声明必须可见并可修订。TS Contract 也应保留现有的 API 约定、持久化与共享约定，而不只是实体和导航名词。

### 日期设计确实缺失

**【已核实】§3.2 没有时间契约。**

- 12306 测试和参考 seeder 都读取 `ARC_TEST_DATE`；相对日期影响查询、过期校验和订单分类。
- ctrip 在 `openHome` 冻结浏览器时钟，服务器时钟不会一起冻结。固定日期还出现在父级需求描述中，不能只读叶子节点。

依据：[12306 seeder](~/projects/arcbench-campaign/upstream/arc-bench/arc-bench/webapp/12306/project/backend/src/database/seed_db.js:12)、[ctrip 时钟设置](~/projects/arcbench-campaign/upstream/arc-bench/arc-bench/webapp/ctrip/tests/helpers.ts:383)。

**【推断】替代：**定义统一业务日期输入：显式环境日期、需求声明的固定日期、浏览器当前日期各有明确用途和时区；种子、UI 和校验共享同一业务日期。不能把服务器真实日期硬塞给所有客户端校验。

## 5. 时间表：最可能拖期的是 §3.3，其次是没列出的集成层

**【推断】§3.3 是研究任务，不是可按接口直接实现的普通模块。** 它同时承担状态规划、断言设计、定位兼容、数据表达式、runner 和判定校准。即使 TypeScript 编译通过，29/32 的门槛仍可能反复失败。

**【已核实】设计还没有完整安置以下交付部件：**

## 7. 最大的一个错误

**【推断】最大的错误，是把“模型输出受限 JSON、执行器复制定位阶梯”当成已经获得可靠验收判据。** 真正困难的是从自然语言补齐准备状态、交互路径和可观测断言；这些判断仍由模型完成，而且会遗漏、过强或与官方路径不同。新设计随即用这些判断控制修复、回滚和交付，错误会被放大成费用浪费与功能丢失。替代方案是先把语义编译器当作待校准组件：保留成熟执行层，先修反馈、共享状态与成果保留，再证明检查能识别已知缺陷；通过校准后才逐步赋予它控制交付的权力。
