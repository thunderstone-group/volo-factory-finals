# 从竞赛目标反推 harness：架构审计与决策

日期：2026-09-12。审计基线：`80955003090c2f50f7a666bfb6f355ebbefbbfbc`。
本轮仅研究与离线诊断：没有真实模型调用、没有官方提交，没有修改运行时代码。

## 结论

**推荐“小型、可替换的编码执行器 + 可信执行/验收控制层 + 有止损的对照实验”，不是继续增加 Ticket 特例，也不是立即重写一个多 Agent 平台。**

下一次模型实验应比较冻结 VOLO 与固定版本 Pi，而不是继续凭感觉修改提示词。Pi 是待验证基线，不是已证明的冠军方案。追踪、环境发现、精确编辑、上下文投影和可重复打包应保留，不应全部推倒。

已有 [harness-research.md](harness-research.md) 在前一天提出了固定基线、验证和迁移评估。因此问题不是从没读过资料，而是原则没有成为可执行的晋级条件。本轮新增：代码审计、三个可重复边界诊断和[下一次实验的判定规则](harness-baseline-plan.md)。

## 1. 从目标反推必要能力

工程目标是在有限费用、墙钟时间和开发者注意力下，让同一 Agent 对不同需求及后续变更，稳定生成实际可验收的软件。正式赛权重未在本轮重新确认，不能凭猜测把内部自测分数或一次公开榜最好成绩当作完整目标。

一次运行依次需要：完整输入、正确解释、形成产物、按约定启动、行为正确、验收可靠观察。提高自测通过率，只有在它能预测真实行为时才有价值。

| 目标/约束 | 必须具备 | 不应因此堆砌 |
| --- | --- | --- |
| 验收实际软件而非文字回答 | 来源明确的场景和真实结果证据 | 模型自己宣布完成 |
| 有限输出与执行预算 | 小粒度动作、有界恢复、验证时间预留 | 无变化地重试整包生成 |
| 有状态和增量需求 | 共享数据/接口契约、纵向功能切片、回归 | 各页面独立生成后碰运气拼接 |
| 未知后续任务 | 通用执行核心、明确任务适配边界 | 将一个题目的选择器约束升级为通用规则 |
| 上下文压缩和执行中断 | 版本化事实、证据状态、可恢复检查点 | 依赖上一段聊天的口头结论 |
| 人的时间与 Codex 配额有限 | 预注册对照、总预算、停止条件 | 因 API 余额多而无限排查 |

2026-09-12 重新请求公开 Ticket API 返回 HTTP 200：1 个任务、10 项测试；规则强调需求文档权威、小步可验证及产物证据。旧正式赛首页只读到动态页面壳，旧 `/rules` 返回 404。本轮未重新确认正式赛全部模型名单、评分权重、日程和测试使用权限。见[公开接口观察](evidence/2026-09-12-research-source-observations.json)。

## 2. 当前卡点：执行是真的，完成判定不够可信

以下源码行号均对应审计基线。

### 验收接口存在，但生产入口没有建立权威验收

`volo/workspace.py:75` 初始化 `required_checks=[]`。仓库搜索只有 `tests/test_fixed_checks.py:18` 对它赋值；`main.py` 没有接入固定验收条件。构建、启动、等待进程是真执行，但 `workspace.py:347–359` 将命令退出码为 0 当作行为检查成功，没有可信场景 ID、实际执行量和覆盖证明。`checks/` 与提供的 `checks/browser.cjs` 也在编码工具可写区域。

本轮用自建微型需求“HTTP 返回 hello”和实际返回 wrong 的应用运行了真实本机 HTTP 诊断：空检查被接受；真正的响应断言失败；只删除失败断言、不改产品源码又被接受。这不是声称真实模型必然这样做，也不是官方任务成绩，而是完成判定的一个可重复反例。

### 截断提示与动作空间互相矛盾

`volo/agent.py:426–443` 在 direct 模式只提供并强制 `build_app`。遇到 `length` 提示少写几个文件后立即 `continue`，跳过 `508–511` 的模式切换。本轮注入四个合成截断响应，四次仍只有整包工具，没有产品产出；这复现了 E050 的控制流问题。

正确不变量是：超出输出能力后，下一步必须允许缩小工作单元；不完整动作不执行；相同无进展状态不能无限重复。只修改提醒措辞不能保证这些性质。

### 局部检查通过，被扩大解释为整批需求通过

`volo/agent.py:527–531` 在批次结束后给所有节点标记通过，却没有逐需求绑定实际场景证据。执行了一个检查、通过若干自测、满足整批需求，是三个不同事实。E049 的 7/7 自测与官方 5/10，E047/E048 同包官方 6/10 与 4/10，均见[实验记录](experiments.md)。

### 看似通用的规则也会过拟合

`volo/web_runtime.py:59–73` 统一禁止多个链接指向同一非首页主导航目标。这源于 Ticket 严格定位失败，但其他需求可以合法要求页首页尾同一入口。没有硬编码 ticket 字符串不等于没有过拟合。英文别名优先、文字唯一出现等策略也须区分：原文明确要求的可观察契约，还是为一个测试形成的实现偏好。

当前缓存保护、精确编辑、原始 trace、源码指纹、工具协议投影仍是有效基础。局部测试通过不等于端到端可靠。本轮也修正 README 中当前最好成绩 5/10 与 6/10、默认预算 300,000 与 450,000 的状态矛盾，历史实验不改写。

诊断：[代码](../scripts/audit_harness_boundaries.py)与[实际结果](evidence/2026-09-12-harness-boundary-audit.json)。本机 Node v22.22.0，不代表官方环境。

这些是作者/维护团队的资料，不同任务、模型与预算下的分数不能直接套用。

| 来源 | 采用的机制 | 不照搬的部分 |
| --- | --- | --- |
| [Anthropic：Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | 逐项实现、版本化进度、浏览器真实验证 | 特征列表与不要删测试的提示不等于防篡改 |
| [OpenAI：Harness engineering](https://openai.com/index/harness-engineering/) | 仓库是事实来源，应用可观察，机械约束不变量 | 不再膨胀一份包办所有细节的提示词 |
| [Pi 官方仓库](https://github.com/earendil-works/pi)、[作者设计说明](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/) | 小工具面，执行、provider、session 分离 | Pi 自身不是权限沙箱；换核心不等于修好验收 |
| [mini-SWE-agent 文档](https://mini-swe-agent.com/latest/) | 简单执行基线让复杂机制接受比较 | SWE-bench 成绩不等于需求生成应用能力 |
| [Anthropic：Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) | 测量最终状态，校准 grader，正反例与隔离重复试验 | 固定错误测试还是错误测试；多个断言不是独立任务样本 |
| [LangChain：Improving Deep Agents](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering) | 固定模型，通过 trace 找失效模式，改变少量因子 | 不把任务特例的提升宣称为泛化 |
| [Anthropic：Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) | 实现前明确完成条件，实际运行验收 | 长时多 Agent 方案不是短预算竞赛配方；模型增强后还应删除不必要流程 |

由此提出：**实现策略保持自由，证据边界保持严格。** 最小执行器不意味着没有验收；有验收也不意味着需要很多 Agent。

## 4. 最小架构：边界，不是六个微服务

```text
原始需求/图片/现有工程 → TaskEnvelope（来源与版本）
                             ↓
                    Controller（状态/预算/恢复）
                             ↓
               WorkerAdapter（Pi 或冻结 VOLO）
                             ↓
               Workspace + Runner → Candidate
                             ↓
               Verifier → Evidence → Controller
外层 Campaign：对照实验、共享账号协调、总预算与晋级。
```

### TaskEnvelope：约束输入，不重新发明需求

保存原始输入哈希、依赖、初始工程、入口、环境、网关、资源上限和验收来源。可提取场景索引：前置状态、动作、可观察结果、原文出处。索引是对原文的解释，不是更高优先级的新需求；或关系不能改成且，缺失条件保留 unknown。

大任务先确定跨功能实体、API、权限/会话、持久化边界，再做可端到端验证的纵向切片。依赖 DAG 有用，但不能只按字符数或页面切分而忽略共享状态。

### WorkerAdapter：通用工具与可替换执行器

接口：`run(task, workspace, budget) -> events + candidate`。负责搜索、读写小文件、精确修改、执行工具与观察；不批准预算、不改权威需求、不为自己签发通过。

默认允许增量写入。整包生成只是测量过的小任务快路，并且必须能退出；三个需求节点不代表一个有状态网站能一次输出。先用 Pi 最薄适配做对照，不把 VOLO 全部规则搬进去。

### Runner：环境约定不是产品逻辑

负责依赖/浏览器发现、构建、启动、就绪、清理及页面/网络/进程证据。3000/3301 属于有版本的环境适配，不应散落到业务代码。轻量 Node 模板可以复用，但不是所有企业应用都必须遵守的单 HTML 架构。

本地复现记录产物、测试包、Node、Playwright、浏览器修订、线程、超时、CPU/内存、数据和网络设置。关键参数未知就称近似复现。固定旧产物重放，用于区分环境噪声与重新生成带来的差异。

### Verifier：同时保证准确性和完整性

区分三类证据：官方验收（按授权范围、只读、单独记分）；开发期可信验收（由需求/允许的公开契约建立，经正反例校准）；执行器自测（可修改的快速诊断，不单独证明全部完成）。不能假设隐藏官方测试在运行时可获得。

冻结测试解决完整性，不保证准确性。E036 已说明第二个模型也会把别名误解为多个控件。可信验收既要接受正确实现，也要拒绝故意缺行为、错误状态、空检查。无法可靠判断的要求保持未验证，不能靠两个模型意见相同升级为真。

不能锁死错误测试：执行器可提出 `challenge_check`，附原文出处和最小矛盾；在独立分支校准新版本，保留旧结果并重评候选。不能边删断言边立即领取通过。

证据绑定需求版本、源快照、环境指纹、验收版本、场景 ID、passed/failed/error/skipped 和产物引用。非零检查数也只是最低要求，不是覆盖证明。缺工具、未运行、评估进程失败、产品行为失败必须分开。

不把部分覆盖伪装成全通过，也不因不可靠自测而无限循环。预算耗尽时，可运行产物应保留，并如实报告部分完成/未验证；是否能交给官方继续评分取决于平台交付约定。

写文件路径检查不是 OS 隔离，任意命令仍可能改文件。可信验收应在可用的只读挂载/不同权限进程/外部评分进程执行；无隔离能力就承认限制。Pi 官方也明确不自带文件、进程和网络权限沙箱。

### Controller：状态与证据推动，而非不断追加提醒

状态：准备 → 实现 → 验证 → 修复 → 候选就绪/部分完成/受阻/预算结束。需求节点只能依据对应证据通过。

| 失败类别 | 通用响应 |
| --- | --- |
| 输出截断 | 拒绝不完整动作，退出整包限制，缩小写入单位 |
| 工具协议错误 | 无副作用拒绝，返回具体错误，限次修正 |
| 构建/启动失败 | 读取对应运行证据，局部修复 |
| UI 超时 | 区分缺控件、脚本错误、未完成请求、环境拥塞 |
| 验收失败 | 保持判据版本，修产品；质疑走独立校准 |
| 连续无进展 | 改粒度/补诊断，或停止该候选 |
| 外部请求结果未知 | 查询原请求/原运行，不盲目重发副作用 |

不变量：没有执行证据不签发通过；源码/验收变化使旧证据失效；损坏动作不执行；不变状态不无界重试；恢复保留已确认工作；留出验证与清理预算。比如预留 20% 墙钟时间可作为待校准起点，不是最佳参数或既定竞赛规则。

### Campaign：约束我们自己如何改进

每个实验先写假设、对照、固定条件、成功/失败判据与最多花费。失败日志必须变成回归或改变明确决策，才算沉淀。统计全部开发成本、人工介入和编码助手配额，不只展示被榜单挑出的成功运行费用。

共享账号的预检不是原子互斥。应采用队友共同遵守的提交协调/租约；平台不支持跨客户端原子性时仍有竞态，上传与启动之间至少重核 latest submission。本机锁不能保护另一台电脑。usage 回包与官方计数不一致时保留两者，不猜测归因。

日常恢复读取短索引：已确认事实、被否定假设、待决问题、下一项实验；原始 trace 留作证据，不每轮把整部流水账塞回上下文。

## 5. 实施取舍与可证伪标准

保留已有解析、哈希、缓存保护、精确编辑、trace、上下文投影、结果分账、打包和 CLI。暂停新的 Ticket 提示词、无对照加预算、失败就换模型、未经校准的 UI 规划层、默认多 Agent 扇出。

每条风格/语义规则记录来源、作用域、正反例、成本和迁移证据；合法重复导航不能被误杀。模型接口兼容分支和失败恢复分支是必要工程，不等同于题目过拟合。

这套方案如果不能减少无效重试、缩小自测与真实验收差距、在相同预算下提高独立任务结果，就不因架构更完整而保留。要证明的是一次失败能够被观察、定位、在不篡改目标的前提下修复，而不是新增了多少类。

**下一项优先工作：外置、可校准的最小评分外壳与 Pi 离线适配，然后第一对固定条件基线。具体见 [baseline plan](harness-baseline-plan.md)。本轮没有实现这些运行时改造。**
