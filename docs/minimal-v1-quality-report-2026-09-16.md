# 极简版 V1 质量实验：完整结果与结论

**本轮未达到推进门槛，不推荐把 V1 当作冲榜版本。** V0 的本地通过率为 13.1%，
V1 Flash 为 16.7%，V1 Pro 为 20.2%；有小幅改善，但跨样本交互仍不稳定。
这里的 Pro 均指 `deepseek-v4-pro`。本轮没有上传、正式提测、推送或合并。

12 次独立生成全部结束，11 份交付、1 份失败；11 份交付应用的原始业务套件全部完成。
共 19 次模型调用，实际已结算 **CNY 16.379350**。没有逐样本业务修复，没有替换低分或失败样本。

## 为什么分数仍低

### 界面约定没有稳定落实到实际交互

六份 Keep 源码均出现了命名编辑器，五份已交付 Bookstack 源码均包含命名登录表单，
说明新提示产生了一些预期变化。但源码里有这些组件，不代表每条操作路径使用了同一个约定。

真实浏览器对首轮 Flash / Pro 两个 Keep 应用的观察显示：

- Flash 的创建按钮实际名为 `Take a note...`，要求精确名称的定位找不到它；同一卡片中有两个
  `Pin note`，原套件实际触发了严格定位冲突。侧栏、部分弹层和操作名称也不匹配。
- Pro 点击 `Take a note` 后出现的是 **内联表单**，标题和内容输入框可见；测试定位的是
  `Note editor` 对话框。源码中的对话框用于另一条路径，不能据源码字符串宣布该创建流程符合约定。
- 两个观察样本均有 19 个笔记 article，且未观察到 JavaScript pageerror。
  因此，不能把这批问题简单归结为应用没启动或笔记数据完全缺失。

部分精确角色、名称和 DOM 包含关系是测试的额外假设，需求未必明确规定。
例如内联编辑器与对话框的区别，不能仅凭这个失败判定所有业务逻辑都没实现。
后续需要把**需求中的明确要求、通用组件约定、测试额外假设**分开；不能将测试专用字符串暗塞进通用提示。

### Bookstack 确实存在可复现的时序问题

原 helper 逐个调用 `isVisible({timeout:500})` 后选择定位器，全部不可见时固定返回按钮定位器。
Playwright 官方说明这个方法立即返回，`timeout` 参数不等待元素出现。
见 [Playwright isVisible 文档](https://playwright.dev/docs/api/class-locator#locator-is-visible)。

在两个首轮 Bookstack 应用上，使用原 helper、原应用、独立浏览器上下文，交错做了
“立即定位”和“等待实际链接可见再调用原 helper”的观察，没有注入网络延迟：

- 立即定位共 4 次，其中 2 次卡在不存在的按钮；失败时实际链接已可见，按钮数量为 0。
- 等待真实链接后，4 次原 helper 点击均可执行；观察中没有 pageerror。

这证明了一个跨样本的入口时序故障，不能据此把后续业务断言改判通过。全部原始成绩保持不变。
Pro 三份 Bookstack 的 81 次失败中，64 次首次阻塞表现为打开命名书架/书籍；该统计是症状归类，
不等于已经证明这 64 次都只有同一根因。

### 更贵的模型和更多推理没有自动解决这些问题

Pro 三份 Keep 只有 2 项在全部三次中通过，与 V0 稳定通过的集合没有新增稳定突破；
Bookstack 仅有一项此前稳定失败的场景转成了三次稳定通过。
本轮 19 次调用中有 7 次 StreamError、1 次 HTTP 400；8 次没有完整 SSE 用量。
这些故障也发生在相同提示词的重试中，不能据此断言是 V1 提示导致了网关故障。
HTTP 错误正文和具体 SSE 错误事件没有被原传输代码保存，精确上游原因仍未知。

## 已收尾的保守修正

这些修正发生在主批次结束后，不回写应用或业务成绩。主批次的原执行器代码保存在 `code-snapshot/`。

1. **动态首页不再因哈希不同触发盲修。** Keep Flash 第三份在返回 HTML 时将
   `__INITIAL_STATE__` 替换为初始数据。它的语法、构建、启动、健康检查均通过，
   原检查器仅因响应与静态文件不逐字相同而判为产品失败。运行检查 v1.1 将这种情况标为
   `unknown`；HTTP 错误、空响应或非 HTML 仍为产品失败。真实产物复验得到 unknown，源码和清理均验证通过；
   新回归还验证了这种未知状态不消费模型修复请求。该应用业务成绩仍为 5/32。
2. **费用与余额变动分开。** 生成阶段余额 56.780702 到 40.401352，差额与 14 条请求账单
   CNY 16.379350 完全一致。评分结束时余额为 240.401352，期间净增加 CNY 200，具体入账原因未查询。
   原 `summary.json` 的最终余额差因此为 -183.620650，原日志也错误地将它标成费用。
   现已修正后续批次的字段和日志；本报告以请求账单为费用来源，保留原始记录。
3. 并发协调日志加了串行写入保护，避免两个开始事件拼在同一行。独立验证了 100 条并发记录均可解析。

90 项相关回归通过，含真实隔离容器验证；四个额外浏览器诊断只用于归因，不计入业务成绩。

## 下一步建议

**暂时不需要再请更强的规划模型推一份大方案。** 已有证据足以把下一步限制在：
提供一份经过验证的页面初始化和基础控件代码，让模型填业务实现，减少它对名称、弹层归属、
操作范围和初始化时机的自由发挥。先用跨任务共用的实现解决这些重复故障，再按冻结批次验证收益。
现有有限修复机制可以保留；本轮结果不支持继续仅靠追加提示词或换模型推进。
这是下一轮建议，本轮没有实施新的组件框架或发起新生成。
