## 三、实现一条固定、可选的运行检查链

建议新增一个小模块，例如 `oneshot/minimal_runtime.py`，接入现有极简版实验入口。保留语法模式及原有默认行为，新增显式开启的运行检查模式。

固定检查顺序：

```text
干净源码副本
  → 语法与静态交付检查
  → frontend 构建
  → backend 启动
  → 健康接口检查
  → 首页可访问性检查
  → 返回带来源的结构化结果
```

以当前 `oneshot/main.py:37–49` 的交付契约为依据，不从离线官方测试反推要求：

| 检查 | 本轮应实际验证的内容 |
|---|---|
| 前端构建 | 在 `frontend` 执行声明的 `npm run build`，确认本次新生成非空 `dist/index.html`。不能让旧 `dist` 掩盖失败。 |
| 后端启动 | 在 `backend` 按声明的启动方式执行，设置明确的 `PORT`，记录真实进程状态、退出码和错误。 |
| 健康接口 | 实际请求 `/api/health`，要求 HTTP 200，JSON 对象为 `{"code":200,"message":"Backend Ready"}`。按对象比较，不苛求空格或键顺序。 |
| 首页 | 实际请求 `/`，确认能返回对应的非空 HTML；只证明首页可访问，不证明交互功能正确。 |

构建和应用代码只能在上述隔离环境中执行。检查结果由可信控制程序根据真实退出状态和 HTTP 响应生成，**不能因为应用 stdout 打印了 `passed` 或一段 JSON 就判定成功。**

每次检查绑定候选源码哈希、检查契约版本、执行环境及阶段结果。构建产生的文件和运行状态不得污染下一候选；发现非预期源码修改、结果与候选不对应、清理失败时，不接受该候选。

### 失败分类必须保留信息，而不是一律送去修代码

沿用 `pass / product_fail / environment_error / unknown`，但每项必须注明验证范围。

明确的应用异常、构建脚本错误，以及实际收到的健康接口错误响应，可以形成有来源的产品失败。Docker 不可用、指定镜像缺失、约定的 Node/npm 工具缺失、执行设施启动失败，应归为环境错误。

**应用违反零依赖契约而引入不存在的包，不应自动被归为“环境缺依赖”。** 区分缺少约定工具与应用自身引入的依赖。

超时、异常终止、输出截断或执行器失联，要记录发生阶段及可见原因；证据不足时保持 `unknown`，不要猜成产品错误。环境错误和未知结果不得消费修复响应。

全部运行检查通过后，仍保持：

```text
behavior = unknown
verified_requirements = []
```

完整业务行为验收不是本轮完工条件，也不能因其缺失而把已完成的构建、健康检查说成无效。
