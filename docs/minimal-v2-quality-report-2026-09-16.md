## 实际改变了什么

只新增两块与任务名称无关的实现：

- `oneshot/v2/interaction.js`：命名按钮和字段、统一编辑器打开／保存／重开、同行重复操作名检查，
  以及留在调用方 DOM 范围内的弹出内容。整页／内联和对话框共用保存状态机。
- `oneshot/v2/navigation.js`：在应用脚本前准备初始数据，基于已准备状态同步切换视图。
  同一源码另复制为后端 CommonJS 文件，避免前端 package 类型影响后端启动。

模型只扩展空白业务骨架，三份共用文件的哈希受到保护；没有 Keep/Bookstack 专用应用模板。
V1 的 system prompt 和原指南保持不变，只添加了实际共用源码及其 API 调用契约。
没有新增规划器、检查编译器、多代理、组件库框架或修复轮数。

检查没有停留在“文件存在”：真实浏览器记录执行过的函数和实际脚本哈希，并检验实际点击后的状态。
Bookstack 第一份的打开、保存、重开与列表、实体导航均完成；第二份也实际执行了共享
`open`、`submit`、`go`、`update`、`renderCurrent`，随后暴露了业务数据同步错误。

## 已定位的业务错误

第二份 Bookstack 修改书架名称后，重开仍显示旧名称。补充的真实请求观察证实：

- PUT 请求发出了新名称，后端返回 200；`entity.name` 和 `domain.shelves` 中都已经是新名称。
- 后端返回 `{ok, entity, domain}`，见该样本 `backend/server.cjs:248`。
- 前端 `mutate()` 却把整个响应交给 `applyDomain()`，它只读顶层 `shelves/books/...`，
  见 `frontend/public/app.js:76–86`。因此新数据没有写进导航状态，重开使用了旧缓存。

这是生成业务代码的接口层级不一致。共用编辑器已经执行了保存回调，不能把它再归为“组件没被用到”。
本轮只定位和观察，没有给这个样本单独打补丁。这个问题提示下一步应检查业务状态闭环，
不能仅因分数未满而继续扩大通用 UI 实现。

相较 V1 Pro 的 Bookstack 失败记录，V2 两份均不再出现此前那类“打开命名书架／书籍时，
固定等待不存在的 button”的主要症状。剩余失败集中在标签区域、确认操作、页面字段、
收藏等更深入的流程，以及部分名称／角色／时序约定。症状消失不等于所有相关业务都正确。

## Keep 为什么尚无结论

两份 Keep 共六次尝试都记录为 StreamError，当前适配器没有提取到可用代码。
整个批次十二次尝试中有十次 StreamError，两个完整答复均来自 Bookstack。
失败流没有完整 SSE 用量，错误正文／具体事件也没有被原传输代码保留；
目前不能断言是网络、上游限制、输入复杂度还是协议兼容问题。

本轮次数上限已经用满，没有继续盲抽。再次调用前应先补齐脱敏的错误事件、结束标记和请求标识记录，
使下次失败可定位。现有两个 Keep 失败记录不能用来证明 V2 组件质量下降。
