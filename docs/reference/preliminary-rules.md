## 提交与成绩

- **正式提交**：
  - 只能由队长账号发起。
  - 每队比赛券 500 元，提交次数不限，用完为止。
  - 使用平台内置的模型 API key，正式评分用的是独立 key。
- **两题同跑，不能并行**：每次正式提交同时运行两个任务，两个任务都结束后才生成这次的成绩。同一队伍不能同时运行两次正式评测，当前提交的两个任务都结束之后，队长才能发起下一次。
- **最终成绩取历史最高分**：从该队所有有效正式提交里，保留成绩最好的一次。
- **练习提交**：用个人 api key 上传平台的练习提交不限次数，分数不计入最终成绩；但它占用队伍的评测资源，有任务在跑时不能提交正式评测。
- **练习券**：每队 100 元 × 5 次，以 api_key 的形式发放，额度低时自动补充。练习券和比赛券的额度都是「暂定保底」，可能追加。

## 计分

- p 是两题合计通过数除以合计测试数（百分数，0～100）。
- b 是两题总开销，单位是元。
- 参数固定：b₀ = 1.2，α = 0.1，β = 0.2。
- 得分公式：
  - p = 0 时，S = 0；
  - b ≤ b₀p 时，S = p / (b/(b₀p))^α；
  - b > b₀p 时，S = p / (b/(b₀p))^β。
- 排名：
  - 按 S 从高到低；
  - S 相同时比较综合通过率 p；
  - p 也相同时比较总开销 b，低者在前；
  - 再相同时比较提交时间，早者在前。
- 取消高低档。**榜单前 20 名晋级决赛。**

对我们的含义（推导，已用数值复核）：
- 在 b ≤ 1.2p 的区间，ln S = 1.1·ln p − 0.1·ln b + 0.1·ln 1.2。费用每翻一倍，只要 p 相对提高 6.5% 就不亏；费用乘以 k，相当于 p 乘以 k^(−1/11)。
- 合并通过率按测试例计。中题 32–34 例、大题 125–135 例时，大题约占 79–81% 的权重。
- 我们的费用远低于 1.2p：两题 2–9 元，而 1.2p 在 40 元以上，所以始终处在奖励区。

## 运行环境

- **镜像**：`mcr.microsoft.com/playwright/python:v1.57.0-noble`，Node 20.19.3，`@playwright/test` 1.57.0，内置 Chromium。
- **资源与测试参数**：每任务 1 核 CPU、2 GB 内存；Playwright 1 个 worker；单测试超时和断言超时都是 10 秒；应用启动最多等 120 秒；目标 URL 为 `http://127.0.0.1:3000`。
- **智能体契约**：
  - ZIP 根目录要有 `main.py` 和 `requirements.txt`。
  - 平台先执行 `pip install -r requirements.txt`，再运行 `python3 main.py <需求目录> --output-dir /workspace/template`。
  - 退出码必须为 0。
  - 输出目录里会预置 `.arc/` 和 `requirements/`。
- **部署**：正式平台只支持根目录下的 `frontend/` 和 `backend/` 结构。`deploy.sh` 只有本地模拟环境支持。
- **外网**：只放行软件源（npm、pip、Cargo 等）和官方 Meter／模型服务。
- **单条流被切断**：网关对单条模型流约 1200 秒硬切断，这是 09-17 到 09-22 的实测，不是文档写明的规则。

## 合规

- **脚手架**：允许与具体任务无关的通用应用脚手架和公共组件库；不允许预置针对当前任务的页面、业务逻辑或功能组件。赛事方会对硬编码、预制答案做自动或人工审核。
- **必须调用大模型**：须知把「不调用或很少调用大模型」的智能体视为固定程序。我们的一次性生成调用模型次数少，所以审核时要能证明业务代码全部来自模型输出。做法是保留生成 trace，平台日志里也有。
- **违规行为**：泄露、推测或绕过隐藏测试，以及绕过网络、资源或评测限制，都算违规。拿不准的做法，先问赛事工作人员。
