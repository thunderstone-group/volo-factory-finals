## 1. 目标

在 09-24 00:00 到 09-30 23:59 之间，拿到尽量高的单次正式提交得分 S。保底进入前 20 名，争取前 10 名。成绩取历史最高分，所以要优化的是「最好的那一次」，而不是平均或稳定性。

**起点**（截至 09-23 09:50，数字都是当时的证据，不是当前状态）：
- 当前候选是 `exp/lite-first-20260922` 上的 v24，未推远端，唯一一次官方运行是 BookStack 9/34。

4. 单次正式提交的费用控制在 10 元以内。费用只有 0.1 次方，通过率优先；但费用越低，500 元比赛券能换的提交次数越多。

- 费用 10 元时，p = 86 对应 S ≈ 108。

## 2. 策略

harness 从「一次起草 + 启发式门禁 + 按问题条数验收的有界修复」，转向「一次起草 + 执行需求场景的验收 + 以场景通过集合为准的迭代修复」。

理由有三条：
- **需求场景是唯一与隐藏测试对齐、又不依赖具体题目的信号。** 须知第 7 问明说测试按需求描述对齐；每个 ATOMIC 需求都带 GIVEN/WHEN/THEN 场景，控件名和角色写得很明确。
- **现有自检看不见渲染结果。** 它的正则契约只认 Lite 两题的句式，丢分最多的结构性错误全部漏过（评审第 1 节）。
- **不再需要为省钱压调用次数。** 费用只有 0.1 次方，单任务可以跑 48 小时，按费用设预算即可。

三条原则：

1. **只做通用的东西。** 不再为练习题或正式题写专属规则、专属探针、专属措辞。
2. **永不交付空。** 任何路径都交付已经完整的最好版本。
3. **用证据晋升。** 机械修复看机制指标加一次真实运行；行为改动看多样本（见第 7 节）。

## 3. 目标架构与现状

| 环节 | 现状（v24） | 目标 |
|---|---|---|
| 输入 | 只读 `requirements.yaml` | 同样只读 `requirements.yaml`，另外把 ATOMIC 场景解析成步骤清单，既给模型看，也给自检用 |
| 起草 | 一次调用写全应用；Kimi HighSpeed；最多续写 1 次；截断落在块间或正文为空就整题失败；Kimi 没有回退 | 一次调用写全应用；默认 flash；截断在任何位置都续写，次数由费用预算控制；正文为空可重试；传输失败有回退模型 |
| 交付门禁 | 构建、语法、启动、jsdom 点击遍历、Chromium 正则契约探针（抽不到契约就不跑） | 构建、语法、启动，加上场景执行自检（每个场景给出通过、失败或未解析）和通用不变量（实体页标题、未知路由显式报错、无 pageerror） |
| 修复 | 最多 2 次；按问题条数验收；整文件重写；验收时不复跑静态门禁 | 按失败场景逐轮修；通过场景只增不减才接受；复跑全部门禁；按费用设预算 |
| 交付 | 任何异常都不交付 | 任何时候都交付已完整的最好版本 |

### 4.2 场景自检

- **目的：** 让自检看得见每一屏渲染得对不对，而且只依赖需求本身。
- **产出：**
  1. **场景解析器。** 把每个 ATOMIC 场景的 GIVEN/WHEN/THEN 解析成可执行步骤。
     - 第一版只覆盖句式固定的步骤：打开应用或某一页；激活名为 X 的链接或按钮；在名为 X 的字段里输入；期望出现名为 Y 的标题、表单、区域、对话框或文本。
     - GIVEN 状态怎么到达：沿需求的 `dependencies` 链，先执行前序场景的 WHEN 步骤。
     - 解析不了的步骤标为 unparsed，不猜。
  2. **执行器。** 在 Chromium 里逐条执行步骤。
     - 每个场景用新的浏览器上下文，后端状态重置到种子数据。
     - 定位语义按公开 helper 的阶梯：先按角色加名字，再按 label、placeholder、文本。这套逻辑自己实现成通用代码，不复制测试文件。
     - 输出每个场景的结论和一句观察，例如「点了 `Shelf 4.2.1` 之后，页面标题是 `Shelves`」。
  3. **通用不变量。**
     - 点击名字等于种子实体名的链接后，主标题要包含这个名字。
     - 未知路由必须显式报错；这一条需要脚手架配合修改，不能再静默回落首页。
     - 页面不出现 pageerror。
  4. **收缩旧探针。** 去掉「抽不到契约就不跑浏览器」的提前返回。Lite 句式专属的 9 类契约冻结、不再扩充，等场景自检覆盖之后删除。

### 4.3 场景验收修复

- **目的：** 修复只针对失败场景，并且只接受不倒退的修复。
- **产出：**
  1. 修复请求只带失败场景和对应的观察。
  2. 接受条件，满足其一即可：
     - 修复后通过的场景集合包含修复前的全部场景，并且至少多一个；
     - 消除了整应用级故障（加载报错、空白页、后端起不来）。
     - 两种情况下，静态门禁都要复跑，不能新增问题。
  3. 预算按费用设，每题一个上限（flash 先按 3 元起步），代替现在的「3 次完成调用」。每一轮都记录费用和场景变化。
  4. 修复范围先保持整文件重发。如果大题上修复经常倒退或超时，另立一项「按屏幕拆文件、只重发被点名的部分」。
  5. 静态门禁只在场景失败时作为补充提示送进修复。单独一条静态问题不再触发一次修复调用（09-23 大题复查：健康的 12306 会因 1 条疑似误报白花一次修复）。
  6. 修复被拒时，记录真实原因。「浏览器复检不可用」要区分两种情况：修复后应用在探针之前就挂了，还是探针本身超时或崩溃。

  2. 在校准集上用公开测试回放核对：所有被接受的修复，都没有丢掉原本通过的用例。
  3. 单题修复费用不超过预算。

### 4.5 模型定型

- **目的：** 用配对数据决定默认模型。

## 6. 正式赛运行规则

**提交前检查：**
- 用的是队长账号。
- 包哈希对应到分支上的某个提交。
- 没有正在运行的正式评测，也没有正在运行的练习提交（练习提交会占用队伍的评测资源）。
- 模型参数正确。
- 本地单测和门禁都通过。

**提交后：**
- 在账本里记一行（见 4.7）。
- 用 `arcbench download` 下载两题产物并归档。
- 用本地场景自检跑同一份产物，记下代理指标和隐藏测试读数的差距。这个差距就是自检的可信度，要持续跟踪。

**比赛券 500 元的分配：**
- 基线读数 2–3 次；
- 候选比较不超过 60%；
- 收官时的最高分重复提交至少留 30%。
- 每天复核一次余额。
- 练习券只用于本地生成和练习平台。

**合规：**
- 包里不出现任何练习题或正式题的专名和业务代码。
- 保留生成 trace，审核时用来证明业务代码全部来自模型输出。

## 7. 证据与决策口径

- **受控修复不算进展。** 受控修复指在冻结的初稿上再修一次，只用来定位原因。
- **比较两个候选：** 每题至少 3 个独立样本。先看机制指标（例如某个失败场景在 N 次生成里修好了几次），再看通过率。单样本对单样本，只能分辨 24–32 个百分点以上的合并通过率差异（附录 3 第 3 节）。
- **机械修复的晋升条件：** 单测加一次真实运行即可晋升。机械修复指消灭整题故障、修传输问题或协议解析问题。
- **本地与官方要分开记。** 每道题先核对本地需求和平台运行时需求是否一致；本地分数和官方分数分开记录，不能互换。
- **一次只改一个机制。** 每个候选都有包哈希，每次改动都进候选分支并带测试。

## 8. 不做的事

- 不再追 Lite 原生 Goal，也就是「同一候选连续 4 次独立满分」。
- 不再为 Keep、BookStack 或正式题写专属规则和专属探针。
- 不把受控修复的分数当进展。
- 没有配对数据时不换模型。
- 不另起新的 agent 框架（mini-SWE、Prime Agent 这一类），历史证据都是负的（附录 2 第 3.5 节）。
- 不同时开多条实验分支而不合并。
- 不读参考图。须知说定位以需求文档为准。
- 生成时的 best-of-2 维持甲方 09-18 的决定，不做。要重新评估，前提是场景自检已经可信（判据 3 达标）。

## 9. 风险与应对

| 风险 | 应对 |
|---|---|
| 正式题的写法和 Lite 不同，场景解析覆盖率低 | 解析不了的步骤退化为通用不变量；第二版再考虑让模型把场景翻译成步骤，但要先过同样的校准判据 |
| 自检误判，驱动了坏的修复 | 「通过集合只增不减」的验收规则兜底；持续对比自检和隐藏测试读数 |
| 网关成簇断流（最坏时段 16 次调用全断） | 重试加回退模型；遇到连续故障先暂停提交 |
| 大题撞上输出上限 | 交付去零加续写。大题摸底里一旦出现 length，或 completion 超过 11 万，就另立「拆分起草」项 |
| 正式题的平台运行时输入与下载版不一致 | 开赛首日核对 |
| 比赛券提前用完 | 每天复核余额；收官预留不少于 30% |
| 合规审核 | 包里没有专名；保留生成 trace |
