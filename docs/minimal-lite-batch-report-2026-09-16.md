## 2. 共性一：运行成功与可操作界面是两层证据

### Keep：名称存在，但角色/范围不符合当前 Lite 定位

三份搜索输入都使用原生 `input[type=search]`。样本 1 的真实浏览器观察：
`searchbox("Search")` 为 1，`textbox("Search")` 为 0；Lite 搜索步骤固定使用后者。
这不是“页面没搜索框”，也不能仅由这个失败断言搜索逻辑不存在。

样本 1、2 的创建入口是带 `aria-label="Take a note"` 的 textarea，Lite 要求同名 button。
样本 3 有该按钮，但后续仍在编辑区域的定位上失败。样本 1 的只读交互证明：点击 textarea
确实能打开编辑器，Title 字段可见，无 pageerror，但 `dialog("Note editor")` 为 0。
另有卡片标题、行操作作用范围、侧栏和菜单命名等重复阻塞，不能把全部 27/28 项都归为创建入口。
创建入口直接阻塞的数量已按原始错误统计纠正；早期口头“多数都卡在创建入口”不成立。

### Bookstack：命名表单和实体入口反复不匹配

三份样本的登录及一批依赖登录的路径都在共同前置步骤阻塞。样本 1 真实浏览器中：
Login 按钮为 1，但 `form("Login form")` 为 0；DOM 有 `login-form`，却没有 aria-label 或
aria-labelledby。Lite 在命名 form 内寻找 Login，尚未走到验证账号密码的阶段。

直接只读访问样本 1 的 `/shelves` 和 `/books`，API 均为 200，分别返回 12 个书架和
16 本书；`Shelf 4.1`、`Book 5.1` 实际可见。书架实体以 link 呈现，heading/button 为 0，
无 pageerror。因此原始失败里“等不到某个 heading/button”不能一概解释为没有种子数据。
这些观察没有证明所有 CRUD 逻辑正确；许多完整流程仍因前置步骤失败而未被真正检查到。

**可泛化的方向是统一输入保真、控件角色/名称、表单/对话框/卡片范围以及动作完成条件，
不是把几个任务的具体标题和测试选择器塞进通用提示词。** 原需求能确定的部分应实现一致；
没有明确提供的角色/范围约束应单独列为信息缺口，不能由自编设计卡赋予验收权威。

## 3. 共性二：Web 与 Lite 不是相同测试的同名子集

已从当前平台接口分别读取两赛道的 Keep/Bookstack 测试。两任务的 Web 与 Lite 文件集合
均不同；当前 Web helper 与 9 月 14 日保留的公开仓库 helper 相同，Lite helper 不同。

- Keep helper：Web `e9c1bc15…`，Lite `42ae20f9…`。
- Bookstack helper：Web `522503eb…`，Lite `d6b74b7f…`。
- 两赛道的需求 YAML/Markdown 也不同，Lite 明确了一些字段名称、反馈文字和 seed data；
  不能声称只是把完全相同的需求换了裁判。`prerequisites_markdown` 两任务均为空；
  本轮生成读取 YAML，未读取参考图。尚未穷尽平台可能下发的其他资源。
- 对已保存的样本 1，只换测试套件，模型、代码、容器、浏览器、worker 和单项超时均不变：

| 相同冻结产物 | 当前 Lite 套件 | 当前 Web 套件 |
| --- | ---: | ---: |
| Keep 样本 1 | 5/32 | 21/32 |
| Bookstack 样本 1 | 4/34 | 6/34 |

这些是诊断回放，不是新生成样本或正式 Web 比赛结果。Keep 的分数对界面定位约定非常敏感；
Bookstack 换套件后仍低，不能把它的失败都归咎 Lite 更严格。也不能根据两个快照推断平台
何时改变了测试，或直接断言测试有 bug。

这解释了为什么旧的本地 Keep 高分不能直接与本批 Lite 低分作能力退化对照。后续所有
比较都必须固定 requirement/test hashes 和执行条件。

## 4. 共性三：就绪时序需要独立检查，不能把嫌疑当根因

Bookstack 两套 helper 的 `firstVisible()` 会即时探测多个 locator，然后选择一个固定
locator；当列表还没渲染时，可能回退到不存在的 heading/button，即使正确 link 随后出现。

样本 1 的只读诊断（app 和原 helper 字节不改）：

- 自然运行：“立即调用 helper”和“等实际 link 可见后调用”都通过，**没有稳定自然复现**。
- 单独的控制实验为 `/api/shelves` 注入明确标记的 **200 ms 延迟**：立即调用选择 heading，
  等待 10,030 ms 后失败，此时真实 link 已可见；等待实际列表出现后，同一 helper 在 7 ms 通过。

该实验复现了时序脆弱性，但不能证明原始 28 个稳定失败都由它引起。等待变体仅用于诊断，
没有替换原始评分、放宽原 suite 的超时或修改产物。它提示下一版要把“后台健康”“当前视图
可操作”“动作完成并可观察”分开处理；仅靠 `/api/health` 无法覆盖后两者。

## 5. 下一步建议：统一改策略，再做新的一批

建议先限定一个明确改动方向：**补齐从任务输入到可操作 UI 的约定，并使界面就绪可观察**。

1. 先核实完整运行时输入和主办方明确提供的界面约定，区分“需求已写却没做到”和
   “评分用了输入未明示的角色/范围”。不从离线失败抄具体答案形成任务特例。
2. 只选择跨这两类应用共用的薄基础能力：稳定的可访问名称、命名表单/对话框、实体标题和
   行操作范围、初始化数据与视图切换的就绪边界。规划/界面清单仅作协作约定，不作为独立通过判据。
   是否需要共享 UI 小组件，应作为下一次单变量实验决定，不一次恢复旧调度和检查编译器。
3. 固定这次统一改动，再对两任务重新生成一整批。保留全部失败、总费用和退步，不修本批六份
   应用来证明收益。随后另留一个未参与这轮设计的任务验证迁移；Keep/Bookstack 都参与了本次
   归因，不能再将其中之一称为完全未见 holdout。

当前证据支持先处理稳定交互阻塞；不支持只增加修复轮数，也不支持宣称极简版已经具有泛化能力。
