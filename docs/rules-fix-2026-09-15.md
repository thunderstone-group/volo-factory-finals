## D2, part 1 — the prompt said two opposite things

The failure feedback for the ambiguity rule ended `and keep the row title in the name`, and
the feedback for the row-title rule said the opposite: name a hover-revealed action `by the
verb alone`. Both were shown to the same model in the same batch.

One policy now, in the prompt, in both messages and in the generator's comments:

* a row action revealed on hover carries the bare verb as its accessible name, and is out of
  the accessibility tree until its row is hovered,
* a row's title is never the accessible name of a hover-only control,
* a row-scoped name (`Archive for Sprint goals`) is **not** forbidden. The evaluator searches
  the bare verb and that name still matches it. It is safe where a row's actions are always
  visible, and the ambiguity rule then applies to them.

`tests/fixtures/synthetic-row-actions-bare-verb.html` and
`synthetic-row-actions-row-scoped.html` are the two accepted shapes, one per naming style.

## D2, part 2 — the container rule checked eight verbs on every row

`auditContainer` ran a fixed list of eight verbs against every row and reported `strayVerb`
whenever the verb existed anywhere on the page and not inside the row, without asking whether
any requirement attached that action to that entity.

It now checks **verb groups** (`more`/`options`/`menu` are one group, as the helpers group
them) and only the groups the requirements declare. `state_runtime.declared_actions` reads the
contract's prose — `exact_texts`, navigation names, entity and field names, seed values,
`persistence`, `conventions`, API purposes — and emits the list as `vocabulary.actions`. Schema
values are excluded on purpose: `navigation[].control` is `"menuitem"` for every sidebar entry,
which declared a row menu in every application with a sidebar, and `kebab` matched
`Note identifiers are kebab-case strings`.

## D2, part 3 — every chooser had to make the page inert

Rule 4 asked a `role="group"` colour palette and a dropdown menu to put `inert` on the whole
page. Only a dialog, or an element declaring `aria-modal="true"`, owns the page now. The
nameless-textbox finding (`exposed`) is a dialog finding only.

The name-collision finding (`leaky`) still applies to every chooser, because its repair is a
rename and not an inert attribute: the sidebar's `Utilities` and an inline picker's
`Utilities for Opening balance` still answer one search, and `menuitem` outranks `checkbox`.
The message now asks for the rename first and for inertness only from a dialog.

## D3 — the overlay lifecycle

Run 5 lost REQ-4.2 to a settings dialog created after an awaited `fetch('/api/settings')`,
which hid the controls outside it in that async path while both restores were synchronous
(`runs/2026-09-14-keep-full-5/app/frontend/public/features/settings.js:63-90`). An open
superseded before its fetch resolved left the page hidden with no dialog. `RD` could not see it
because it reloads the page between the click and the assertion, and a reload repairs it.

Three pieces:

1. **A harness-owned module**, `volo/web_runtime.py:OVERLAY`, served at `/factory/overlay.js`.
   `openOverlay(id, render)` returns a handle carrying the open sequence; `handle.isCurrent()`
   is what late work asks before touching the DOM; the module owns making the rest of the page
   inert, on the same synchronous path that creates the container, and one cleanup serves every
   close route — `closeOverlay(id)`, `handle.close()`, Escape, a superseding open, and product
   code that removes the container (a `MutationObserver` catches that one). `{modal: false}`
   opts a menu or palette out of inertness.

   The build emits it into `frontend/dist/factory/`; it is **not** shipped in
   `frontend/public/`. Shipping it there creates that directory before the model writes
   `index.html`, and a batch that writes no `index.html` then builds successfully and waits out
   the 30-second readiness poll instead of failing at once with `Frontend build failed`. That
   cost was measured: `ScheduleCompletionTests` went from 0.6 s to 60 s, and the whole suite
   from 193 s to 461 s.

2. **Prompt text**: rule 7 of `INTERFACE_RULES`, with the four-line example, and the file listed
   in `STORE_CONTRACT` among the files the model must not rewrite.

3. **A same-page check**. Every control the one-click walk finds to open a dialog is driven on
   one page, without reloading between the steps: open and close; open and close again;
   supersede the open with a second one; interrupt the open with the application's next
   control. Each ends by dismissing whatever is open with the application's own close control,
   and then asserts that no dialog is left open, that the same dialog is not open on top of
   itself, and that no control the entry page carried is now present but unreachable. Finding
   name `overlayLeak`. A probe whose overlay the check could not close reports nothing.

   The supersede and interrupt probes hold the application's `/api/**` responses back for
   500 ms through `page.route`. The race is latency-dependent — the hosted runner manages about
   two calls a minute — and on a developer machine a local request resolves between two
   Playwright clicks.

   Budgets: at most 4 openers, 13 s for the phase, and the interrupt probe runs for the first
   two openers only. `WALL_BUDGET` went from 25 s to 36 s to make room.

## The thirty-second write, and what it cost

An earlier shape of this work shipped the overlay module as `frontend/public/factory/overlay.js`
through `install()`. That created `frontend/public/` before the model wrote `index.html`, so
`frontend/build.cjs` stopped failing on a missing `public/` and the application started and
served 404 at `/` instead. Every verification then sat out the thirty-second readiness poll at
`volo/workspace.py:897`, which is why one `write_files` took 30.2 s, and two tests failed on the
same cause: `SourceBudgetTests` read the new `factory/` directory as a file, and
`VocabularyModuleTests` pinned the exports line without `actions`.

Emitting the module from the build into `frontend/dist/factory/` removes the cause; the two
tests are fixed. Measured on this branch, the same commands:

## Open: the row menu the contract cannot see

`declared_actions` accepts an optional `requirement_text`, and `state_runtime.install` and
`contract_files` pass it through. Nothing supplies it, because `volo/agent.py:1747` calls
`state_runtime.install(self.workspace, self.contract, self.observed_texts())` and the
requirement package is not in the workspace.

It matters for Keep. `More options` appears in the requirement prose
(`keep/requirements/requirements.md`) and is never quoted, so it never reaches `exact_texts` and
the contract cannot declare the `menu` action:

```
contract only : ['archive', 'color', 'delete', 'labels', 'pin']
with prose    : ['archive', 'color', 'delete', 'labels', 'menu', 'pin']
```

That is why the two `menu` findings disappear from the table above. The composer defect behind
REQ-2.7.4 is still reported through `labels`, which resolves to the sidebar's `Edit Labels`, so
nothing is lost silently — but the `menu` half of that failure is no longer checked.

The minimal change, for the team lead to route, is one argument at `volo/agent.py:1747`:

```python
state_runtime.install(self.workspace, self.contract, self.observed_texts(),
                      self.requirements.batch_text(self.requirements.nodes))
```

`RequirementSet.batch_text` already exists (`volo/requirements.py:104`) and returns the plain
requirement text for a set of nodes; over the whole Keep package it is 11,694 characters, and
it is what turns the list above into the one with `menu` in it. No other file needs to change;
`install`, `contract_files` and `vocabulary_module` already take the argument and default it
to `None`.
