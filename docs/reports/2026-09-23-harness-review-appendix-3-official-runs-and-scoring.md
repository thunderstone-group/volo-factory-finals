## 结论先行（第 6 项：从数据看，什么最限制初赛分数）

1. **最限制分数的是大题通过率。**
   - 合并通过率按测试例计数。一中（32–34 例）一大（125–135 例）时，大题占 79–81% 的权重，每个测试例约值 0.61 个百分点。
   - flash 主线 r14–r27 共 14 个包、每题 28 个样本。其中 12306 平均通过 50.3%，Ctrip 25.8%，中题 Keep/BookStack 已经在 79% 左右。
   - 中题再涨 10 个百分点，合并通过率只涨约 2 个百分点；大题涨 10 个百分点，合并通过率涨约 8 个。
   - 把同一轮的两题配成对算，Keep+12306 型组合的合并通过率均值是 55.8%，Keep+Ctrip 型只有 36.6%（`analysis-output.txt`）。

2. **采样噪声比 r14–r27 所有包之间的差异都大。**
   - 同一个包同一道题跑两次，有 14–28% 的测试例结果会翻转。相邻两个包之间的翻转比例是 12–34%，和前者一样多。
   - 六题均值在同一个包内的标准差是 6.0 个百分点，而 14 个包的均值彼此之间只差 5.4 个百分点。单因素方差分析的 p=0.19；剔除已被否决的 r18、r23 后 p=0.96。
   - 一次一中一大提交，合并通过率的单样本标准差约 9–12 个百分点。
   - 如果用一两个样本比较 prompt 或卡片改动，只能分辨出 12–17 个百分点以上的六题均值差异。

3. **费用几乎不影响分数，花钱换通过率是划算的。**
   - 我们观测到的费用全都远低于参考费用 1.2p，始终处在奖励区，此时 ln S = 1.1 ln p − 0.1 ln c + 常数。
   - flash 跑一中一大两题实付约 2.0–2.5 元，参考费用约 44–67 元。
   - 费用减半，只相当于通过率相对提高 6.5%（p=50 时是 +3.25 个百分点）。反过来，费用翻倍只要换来 +3.6 个百分点（Keep+12306 型，p≈56）就不亏。
   - 费用项在 ln S 的方差里占不到 1%。
   - 换成 Kimi HighSpeed（两题估计 8.7 元）相当于通过率少 6.6 个百分点；换成 Qwen3.7-plus（约 1.3 元）相当于多 3.2 个百分点。这两个数都小于单次提交本身的噪声。

4. **第二大损失来源是整题丢失和传输故障。**
   - flash 的模型调用里，19.4% 以 StreamError 结束（136/702）。这些失败成簇出现：09-17 19–23 时 32 次调用失败 23 次，其中 20–22 时 16 次全断；09-18 20–21 时 47 次失败 39 次。
   - r13–r27 有 25.5% 的 run 至少有一次调用失败，这些 run 中位多耗 565 秒。
   - 加上同模型重试和回退到 qwen3.7-plus 之后，整题未交付降到 1.8%（4/220）。另有 2.7%（6/220）的 run 交付了应用，但测试几乎全挂。
   - 两者合计，每题约 4.5% 会整题丢失；一次两题提交约有 9% 的概率丢掉一题。
   - 慢模型还会撞上网关的 1200 秒断流。qwen3.7-plus 失败的 7 次调用里，有 4 次正好断在 1200 秒；kimi-k2.7-code 本地跑 BookStack 也在 1200 秒断流。

5. **我们用来判断改进的两把尺子都有系统偏差。**
   - 平台给每条 run 记的费用，是整个共享 key 在该 run 时间窗口内的计量增量，并发的 run 会互相重复计入。09-17 以来平台记录的费用合计 4380.8 元，估计实付只有 468.2 元，虚高 9.4 倍。
   - 本地 Lite 回放用的是公开需求，而官方运行时给 Keep 的输入和公开版有 85 处语义差异。同一个 qwen v5 包，本地独立生成 Keep 得 29/32，官方只得 14/32。
   - 按本地 Lite 分数或平台的费用字段做取舍，会系统性地高估通过率和费用。

### 0.1 平台费用字段不能直接用

平台对每条 run 记的费用和 tokens，是 run 开始和结束时对整个 access key 各拍一次计量快照、再相减得到的。日志里对应 `Meter baseline captured for access key` 和 `Meter usage captured` 两行，官方模拟器 `local_submit.py` 第 535–576 行也是这样实现的。

**单独运行时，这个值是准的。**
- 57cf6c6841da 记 6.458581 元，正好等于它窗口内 174 条计费请求之和。
- 官方 qwen Keep（2eef0a0f987a）记 0.665106 元，等于 0.515096 + 0.150010。
- 官方 Kimi BookStack（fd8ba0b84fe7）记 3.821024 元，等于 2.941540 + 0.879484。
- 以上请求明细都在 `requests.json`。

**并发时会重复计入。**
- r26b 的 12306（194ddc3c3f11）和 Prestashop（cfa73098cd54）都记 17.388194 元。
- r24 Lite 的两个 Keep（1056fe3b0665、8b81e4d10dc1）都记 18.865343 元。
- r27 Lite BookStack（1b3a6ea54535）只完成了 1 次调用，却记 11.104056 元。

**并发 run 的实付费用用反卷积估计。** 思路是：每条 run 的窗口增量，等于这个窗口内所有已完成模型调用的费用之和。
- flash 单次完成调用的费用建模为“固定部分 + 每秒费用 × 流式秒数”。
- 断流失败的调用不计费。09-22 Kimi 有两次修复调用断流，`requests.json` 里没有对应账单，和 09-17 的记录一致。
- 剔除与智能体式 harness run 重叠的窗口后，用 344 个窗口做稳健拟合，得到每次调用 0.243 元、每秒 0.000992 元。bootstrap 90% 区间分别是 0.165–0.325 和 0.00081–0.00117，R² 0.93（`cost-fit.json`）。
- qwen 回退调用按 09-22 实测吞吐，固定为每次 0.05 元加每秒 0.000552 元。

**校验结果：**
- 11 条单独运行的 flash run，估计值和计量值平均相差约 8%。例如 435556e82b15 计量 1.889 元、估计 1.879 元；8418091af0b5 计量 0.710 元、估计 0.709 元。
- r24–r27 四轮 64 条 run，估计合计 76.61 元。进度账本记录余额在 r24 前是 116 元、r27 后约 40 元（`lite-first-20260922/docs/progress.md` 第 424、501 行），实际花掉约 76 元，两者一致。平台对这 64 条 run 记的费用合计是 992.22 元。
- 智能体式 harness（s8h/pi，共 18 条）没有逐调用时间，改用它自报的 token 用量乘 0.503 估计。这个系数来自单独运行的 57cf6c6841da：自报用量折合 12.84 元，实际计费 6.46 元。

## 4. 评分敏感度

### 4.1 公式与弹性

公式在 `local_submit.py` 第 230–244 行：
- p 是精确通过率（0–100），c 是计量费用（元），参考费用为 1.2p。
- c ≤ 1.2p 时，S = p / (c/(1.2p))^0.1；否则指数改为 0.2。
- p ≤ 0 时 S = 0；c ≤ 0 或缺失时，本地实现不给分。

在 c ≤ 1.2p 时，S = 1.2^0.1 · p^1.1 · c^−0.1，因此 ln S = 1.1 ln p − 0.1 ln c + 0.1 ln 1.2，常数为 0.0182。你给的式子核实无误。
- S 对 p 的弹性是 1.1，对 c 的弹性是 −0.1。
- c > 1.2p 时，弹性变为 1.2 和 −0.2。两段在 c = 1.2p 处连续，此时 S = p。
- `score.py` 用数值微分复核了这四个弹性。

我们不会进入惩罚区：两题费用 2.5 元时，通过率要低于 2.1% 才会让 c > 1.2p。

### 4.2 换算表

| 当前 p | 费用减半相当于 p 提高 | p +1 个百分点相当于费用乘以 | 费用翻倍需要 p 提高 |
|---|---|---|---|
| 40 | +2.60 个百分点 | 0.76 | +2.60 |
| 50 | +3.25 | 0.80 | +3.25 |
| 60 | +3.90 | 0.83 | +3.90 |
| 70 | +4.55 | 0.86 | +4.55 |

一般规律：费用乘以 k，等价于 p 乘以 k^(−1/11)。费用减半等于 p 相对提高 6.5%；费用乘以 10 等于 p 相对下降 18.9%。

### 4.5 （c）大题在合并通过率里的权重

合并通过率 = 两题通过例数之和 ÷ 两题例数之和。每个测试例权重相同，所以大题的权重就是它的例数占比：32+135 时为 80.8%，34+125 时为 78.6%，33+130 时为 79.8%。每个测试例约值 0.61 个百分点。

flash 的中题已经在 79% 左右，大题在 26–50%。大题每提高 10 个百分点，合并通过率提高约 8 个百分点，S 相对提高约 16%（p≈56 时）。中题每提高 10 个百分点，合并通过率只提高约 2 个。

### 4.6 在这个公式下谁更占优

- **在相同通过率下，价格影响有限。** 最便宜的 qwen3.7-plus 比 flash 高 6.8%，kimi-hs 比 flash 低 11.6%。这些差距折算成通过率只有 −3.2 到 +6.6 个百分点，都小于一次提交合并通过率 9–12 个百分点的标准差。选模型应该看大题通过率和交付稳定性，价格是次要因素。
- **只有 flash 有大题数据**（12306、Ctrip 各 28 个样本）。qwen3.7-plus 只有 09-17 旧包上的单样本：12306 63/135（ae507f83ee7a），Ctrip 12/125（ba63aa5e2be5）。kimi 的两个型号没有任何大题数据。

## 附：口径与局限

- 并发 run 的实付费用是估计值。单独运行的 run 平均误差约 8%，四轮合计也和余额账本对得上，但单条 run 的估计可能偏差 ±20%。结论 3 只依赖费用的数量级，不受这个误差影响。
- 平台的 `tokens` 字段和费用字段一样，是时间窗口内整个 key 的计量，并发时同样虚高。
- 须知说正式赛使用“独立 key”（`preliminary-notice-20260921/docs/reports/2026-09-21-preliminary-notice.md`），但没说是每队一个还是每次运行一个。如果一队的两题共用一个 key 并发运行，按模拟器的实现，两题的计量会互相重复计入，c 最多翻倍，相当于 S 下降 6.7%。
- 各模型之间的比较混有候选改动：qwen 的 Lite 样本来自 v3–v5，kimi-hs 来自 v12–v24，flash 的 Web 数据来自 r14–r27，三者都不是同包对照。
- 初赛两道隐藏题“一中一大”是口头信息。本报告用 Keep/BookStack 代表中题、12306/Ctrip 代表大题，隐藏题的实际难度可能不同。
