# 2026-10-02：两题泛化瓶颈与 S70 实验依据

截至 06:25。正式最佳仍为同提交 GitHub 24、Sheet 81，S 59.7517；最新完整正式候选为 27、73，未提升整体。本文判断来自代码、公开需求、实际生成产物和执行证据。榜上其他队伍的模型名和通过率不能证明他们采用了哪种架构。

## 主要判断

当前首先需要修正的是反馈与验收架构，其次是把业务方法落实成可执行约束。不能只归为模型不够强，也不能靠继续增加普通测试数量解决。我们已经能生成可运行的复杂应用，但“自己写的测试通过”与“满足需求”之间仍有很大距离。

同一份正式产物的对照最能说明问题：

| 产物 | 当次生成的自测 | 固定独立书面裁判 | 正式测试 |
| --- | --- | --- | --- |
| GitHub | 112 过、13 未判定 | 69 / 66 | 27 / 100 |
| Sheet | 112 / 112 | 89 / 93 | 73 / 100 |

各独立裁判有 100 个原始场景；自测还包含追加诊断，分母不同。由于是同一份产物，这个落差不能用“本地和线上随机生成了不同代码”解释。正式接口没有返回逐条失败，因此也不能据此断言某个具体缺陷就是隐藏失分原因。

## 两题的共同难点

| 任务 | 需要同时成立的约束 | 已执行复现的反例 |
| --- | --- | --- |
| GitHub | 记录历史必须保留，但权限和有效决定必须随身份、当前提交和最新操作变化；同名实体的身份由所属空间共同决定 | 同一 reviewer 改为 Comment 后旧 Approve 仍允许合并；compare 分支新增提交后旧审阅仍有效；跨 owner 的同名仓库被误判重复；过长标题覆盖原值 |
| Sheet | 数据内容、坐标和引用不是同一个东西；行列变更要同步维护公式、验证规则和关联范围，同时保留不受影响的数据 | 删一列后其他行的数据被重新排列；插行后透视表刷新仍读旧范围；相对引用越界未报错；非法单元格引用返回空值而非错误 |

共同矛盾在于：一个局部操作改变了某些事实，但其他事实必须保持不变，依赖它的结论又必须重新计算。按钮存在、成功提示出现、当前示例显示正确，都不足以证明这些约束成立。实现需要统一的身份、状态转换和派生规则；验证需要合法前置状态、实际操作以及对相关结果和不变项的观察。

## 代码中如何形成盲区

1. **先整包生成，再以有限测试补洞。** `draft_messages` / `draft_application` 要求一次输出完整应用，业务通常集中在一份很大的 `app.js`。多个工作流容易各自实现近似规则，缺少一个共同维护的有效状态定义。GLM 路由的完整应用调用曾在 16,384 输出 token 全用于推理、没有代码的情况下结束，说明当前生成方式还受实际输出窗口制约；这不是对厂商模型上限的判断。
2. **测试与实现会共享需求误读。** `testgen.write_suite` 根据相同需求写浏览器测试，但并不能机械证明测试语义正确。某些检查只确认可见提示，某些前置条件被跳过，某些额外布局或名称限制反而拒绝正确路径。正式 GitHub 的 13 项未判定中有 7 项名称依据判断和 6 项跳过；它们不是功能通过。
3. **修复目标是代理测试收益。** `repair_request` 和 `judge` 用失败转通过、回退数量及通用守卫决定收下哪次修改。这个机制能够修复真实 UI 问题，但无法自动纠正测试与需求之间的语义偏差。三比一收益规则也不能把低可信的测试变成可靠验收。
4. **历史经验大多落在提示和定位规则。** `dialect.md`、共享脚手架和静态检查解决了交付、可访问名称、事件与共享存储问题。对有效决定替换、引用迁移、拒绝时保留原值等业务约束，原先缺少另一条能执行并反驳实现的检查路径。

因此，架构问题主要是验证信号不足和相关误差；方法问题主要是跨功能约束没有进入可执行检查。继续增大同类测试集会增加费用，却可能继续遗漏同一类问题。

## 本次已做的改变及证据边界

先尝试恢复被跳过的 UI 场景，但在三个冻结产物上仍出现前置状态和定位范围错误，已撤下该原型。没有把这些失败当成产品缺陷。

当前候选增加一次代码反例审查：模型读公开需求和当前代码，提出至多四项反例；执行器绑定实际函数，先验证合法前置状态，再执行操作和断言；第二次模型调用校验夹具与语义。修复时冻结反例定义，并重新绑定修改后的代码。错误夹具不算缺陷，错误转通过不算修复收益；它们也不产生 `verified_requirements`。

模型自动校验后的八项反例在原产物均失败，在受控修复产物均通过。未参与修复的独立浏览器裁判，GitHub 保持 69/66，Sheet 从 89/93 提到 90/96。初始受控修复输入经过人工校准，因此这组证据只证明机制能发现并修复遗漏，不能代替自主生成和正式评测。

候选关闭上一轮默认追加的 UI 审查，避免直接叠加费用。精确包已开始全新双题生成；接下来以独立回归、完整正式双题终态、总费用和同提交 S 判断去留。S ≥ 70 才完成用户目标。

若局部反例通过而正式仍不改善，下一步应检查完整前置状态和实际 UI 路径，并比较按依赖逐步实现的生成方式；不应继续堆反例数量，也不能把同一组示例修好称作泛化提升。
