## 结论先行

1. **时间和费用都由推理量决定，探针不是瓶颈。** 这个包的做法是：一次 Kimi 大调用写完整个应用，再用确定性检查找问题，最多再花两次调用修。模型调用占墙钟约 93–98%（官方 92.9%），输出 token 占费用 83–91%，输出 token 里 61–85% 是推理。探针加 npm 只占墙钟 2–7%。

3. **对初赛分数威胁最大的是大题。**
   - 按「一中一大」，大题在合并通过率里占 59–80% 的权重。
   - 当前 Kimi 候选从没在 100 例以上的题上跑过。
   - 单次调用的 131,072 上限同时装推理和正文。撞上限后，代码里有三条路径直接不交付，即整题 0 分。
4. **第二大威胁：「页面渲染了错误的实体或错误的屏」没有任何通用检测。** BookStack 上这类错误已有 4 次记录（13/34、5/34、9/34、9/34）。09-18 账本里就写下了对应检查的设想（点实体链接后，标题应变成链接文字），一直没有实现。

## 3. 结构性瓶颈与风险

### 3a. 单次起草调用的规模上限

**结论：** 大题最先撞的是「单次 131,072 token 同时装推理和正文」这道墙。撞墙后，多数处理路径是整题 0 分。续写机制只覆盖一种截断位置，而且从未在 Kimi 上跑过。

1. **中题的实际用量。**
   - Keep 起草输出 32,125–63,077 token，其中推理 21,924–54,501。
   - BookStack 起草输出 39,619–65,004 token，其中推理 27,748–49,685。
   - 正文 29,932–46,727 字符。官方 v24 正文 36,822 字符对应 11,587 token，约 3.18 字符/token。
2. **大题的规模。**
   - 需求字符数：12306 为 137,814，Ctrip 为 114,776，分别是 BookStack（38,919）的 3.5 倍和 2.9 倍。
   - 按 v24 的组装方式，12306 的 user prompt 为 197,734 字符（约 4.9 万 token），Ctrip 为 171,959 字符。
   - 脚手架时代大题产物中模型写的三个文件有 89–131 KB，约合 2.8 万–4.1 万正文 token。样本：`~/projects/volo-factory/runs/2026-09-18-goal/r19a-bundle-ctrip`、`r17a-bundle-ctrip`、`r27a-12306-bundle`、`2026-09-20-goal/r28a-12306-bundle`。
   - Web r18b 的 Ctrip 单个 app.js 写到约 200 KB 才被截断（`WT/docs/progress.md:263-265`）。
3. **撞墙点（推断）。**
   - 正文要 2.8 万–4.1 万 token，留给推理的空间只剩 9.0 万–10.3 万。
   - 大题推理只要达到 Lite 最高值（54,501）的 1.65–1.9 倍就会撞上限，而需求文本是 Lite 的 2.9–3.5 倍。
   - 「max_tokens 也约束推理」对 Kimi 没有直接测量。间接证据：kimi-k3 在 max_tokens 12000 时，以 12,372 token 结束于 length（`progress.md:25`）。
4. **撞墙后的三条不交付路径：**
   - **推理耗尽、正文为空。** 抛 `ValueError`，不在重试分支里，整题 0（`main.py:281-282`）。GLM 在 32,768 上限下这样 0 分过两次（`progress.md:32-33`）。
   - **截断恰好落在两个文件块之间。** 直接抛错。即使脚手架能补齐缺的文件，也不交付（`main.py:1095-1097`，且被单测锁定）。
   - **截断在文件块内部。** 只能续写 1 次，而且要求「从文件开头重写」（`main.py:94-97`）。大题里被截断的几乎必然是最大的 app.js，续写要整份重写一遍，同时 Kimi 常开推理会再推理一遍。续写再被截断就失败（`main.py:1099-1100`）。flash 实际走过这条链：首次到 95,200 token 时 length，正文只有 13,606 字符；续写到 71,296 token 又 length；最后以 unterminated file block 失败（`progress.md:111-114`）。
5. **没有分段机制。** 「大题 planner 阶段」在 09-18 被列为未开始（`progress.md:372-374`）。
6. **当前候选在大题上的证据为零。**
   - `R/generations` 下没有任何 12306 或 Ctrip 生成。
   - 最近一次大题生成是 09-20 用 deepseek/qwen 跑的，两题都在 5 次传输失败后 0 交付（`~/projects/volo-factory/runs/2026-09-20-goal/gen-12306/gen.log`、`gen-ctrip/gen.log`）。
   - 时间不构成墙：一次 131k token 的调用约 11 分钟，平台日志显示代理容器「Waiting for container to exit without timeout」。
7. **权重。**
   - 中题 34–86 例、大题 125–135 例时，大题占合并通过率 59–80%。
   - 大题 0 分后，p 很低，费用可能超过 1.2p，指数随之从 0.1 跳到 0.2。例如 p=5、c=8 时 S=4.72，比 p 还低。

### 3b. 语义探针的覆盖模型

**结论：** 探针能看见两类东西：崩溃，以及需求里用特定句式写明的少数交互契约。它看不见「这一屏渲染的内容对不对」。路由错误还让详情页不可达，反而使依赖详情页的检查空转通过。

**能检测的失败类别：**
- **崩溃类：** 构建失败、语法错误、后端起不来、`/` 类型错误、加载即报错、空白页、页面卡死、点击处理器抛异常（`main.py:801-874, 602-749`；`semantic_probe.cjs:128`）。
- **需求派生契约：** 用 41 处正则从 YAML 原文抽取（`main.py:507-599`）。例如：
  - 「article/card/record … opens … dialog named X」（`523`）
  - 「X list on the homepage」和「The homepage shows」（`525-537`）
  - 「button named Favorite with aria-pressed=false」（`540`）
  - 「control named X that reveals a textbox with exact placeholder Y」（`567-570`）
- **交互机制：** `data-action` 是否真的送达处理器、原生复选框能否翻转（`semantic_probe.cjs:287-327`）。

**v24 路由错误为什么漏过：**
1. **没有「目的屏对应被点实体」的不变量。** 遍历只跑与内容无关的 `scanSemantics`（`semantic_probe.cjs:4-124`），也不识别「not found」文本。官方产物 `#/books` 渲染的是 `<h1>Book not found</h1>`（`app.js:206`），`#/shelves/<id>` 渲染的是列表（`app.js:301`）。
2. **探针确实访问过这些坏页。** `smoke-final.json` 的 `screens` 里有 `#/books` 和 7 个 `#/shelves/shelf_*`，但一个问题都没报。
3. **契约检查被错误页面「满足」了。**
   - `recordActions` 检查要求 Shelf 4.3.1 详情页上有 `New Shelf`（`semantic_probe.cjs:210-216`）。坏路由把详情页渲染成了列表，列表正好有这个按钮，于是检查通过。
   - 修好路由后，真实详情页没有这个按钮，本地复跑立刻报出。
   - 官方 REQ-4.3.1/4.3.2 正是因此失败（`R/replays/diagnostic/official-v24-router/result.json`）。
4. **通用遍历几乎只点品牌按钮。** 页头按钮优先级为 0 且位于 DOM 最前；点完就跳回首页，这一屏的遍历随即结束（`semantic_probe.cjs:276-283, 339`）。官方首轮 15 次点击里有 12 次是 `BookStack`，修复后 13 次里 10 次。
5. **静态门禁读源码，不读渲染结果。**
   - `Create New Book` 按钮只存在于从未被调用的 `booksList`（`app.js:199`），另一处是表单标题（`app.js:86`）。引号词门禁按源码文本匹配，照样通过。REQ-5.3.1/5.3.2 正是在等这个按钮时超时。
   - `shelfDetails` 和 `booksList` 在 app.js 里各只出现 1 次，就是它们自己的定义。一个「定义了但从未被引用的屏幕函数」检查就能直接指出问题。
6. **脚手架只按 URL 第一段分发，未知路由静默回落首页。** 参数分支完全留给模型写（`scaffold/.../lib/arc.js:24-26`、`scaffold/.../app.js:38`，官方产物 `app.js:318` 照抄）。链接形状和屏幕注册一旦不一致，就会不报错地渲染成别的屏。Web r18a 就是这类不一致（`progress.md:275-277`）。

**这类错误的历史记录，每次损失 20–29 例（官方 v24 仅两行修正就 +21 例）：**
- Web r18a BookStack 13/34。
- 09-22 DeepSeek 5/34；修正一处回调接收者后 29/34（`progress.md:552-555`）。
- v22-a Kimi 9/34。这次抛了 `this.X is not a function`，探针抓到了，但修复调用断流（`R/generations/form-state-v22/bookstack-highspeed-a/trace.json`）。

**覆盖上限：** Chromium 遍历 ≤12 屏、16 s；jsdom 遍历 ≤40 屏、15 s。对大题，这意味着只有极小一部分屏幕会被碰到（推断）。

### 3d. 修复循环

**接受与回滚：**
- 每轮先整目录备份。异常或不达标时，回滚到本轮备份；追加修复失败时，只回滚到上一轮已接受的版本（`main.py:1463-1464, 1518-1531`）。
- 验收核心是**问题条数**（`main.py:1491-1499`）。另有两道护栏：引号词缺失数不增加（`1500-1502`），需求点名的控件名不被改掉（`1505-1513`）。

**预算耗尽：** 完成调用满 3 次或失败满 5 次后，直接交付当前版本，并记录 `skipped`（`main.py:1457-1459`）。续写要占一次完成调用，大题上修复次数会被压到 1 次（推断）。

**传输失败：**
- 同一请求重试，间隔 1 s，每次调用最多 3 次尝试，失败次数计入全局上限 5，部分输出全部丢弃（`main.py:285-309`）。
- v22 两局修复调用出过断流：一次在 108.6 s 被重置（curl 56，已收 31,210 推理字符），一次在 61.7 s 空响应（curl 52）。当时修复不重试，于是交付了未修的 9/34 和 30/34（`SESSION_HANDOFF.md:48-60`）。v23 起修复也有 3 次尝试。
- 失败调用平台不计量，费用是未知，不是 0。
- 官方走 urllib 而不是 curl，同类断流会表现为 IncompleteRead、OSError 或 StreamError，处理路径相同。

**「修复把好的改坏」的防护不充分，两个方向都有实锤：**
- **误收。** v4 BookStack 起草 28/34，静态门禁只报 1 条撞词；修复被接受后降到 23/34（`R/bookstack-v4-draft-replay.log`、`R/bookstack-v4-direct-a-replay.log`、`R/generations/targeted-contract-v4/bookstack-direct-a/trace.json`）。那是 qwen 和 v4 的规则，该误报门禁后来修了，但按条数验收的机制没变。修复会整份重写 app.js（官方这次 21,472 字符），验收却只看探针能看见的那一小片行为。
- **误拒。**
  - v12 Keep 的干净修复被控件名护栏拒收，交付 25/32；那份修复本身能到 32/32（`SESSION_HANDOFF.md:186-190`，v13 已补）。
  - r26b BookStack 修掉 6 个抛异常的处理器，但暴露出 1 个新的，被拒收后交付 9/34（`main.py:1494-1498` 注释）。
- **按规则推演出的新误拒（推断）。** 官方 v24 首稿有 2 条族级问题。假设一次修复在修这 2 条的同时也修好了路由，复检会报路由修正版上的 6 条问题。6 不少于 2，按 `main.py:1491-1499` 会被拒收，最终交付的是带路由错误的首稿。页面变得可达后问题条数上升，这是计数规则的系统性偏差。
- **静态门禁在验收时不复跑**（`main.py:1484-1513`）。修复新引入的撞词、只读输入、缺失的进程守护、被删的脚手架原语，验收时都看不见。

## 4. 最卡分数的前 5 个瓶颈（按对初赛分数的影响排序）

### 瓶颈 1：大题单次调用上限，截断即 0 分

- **为什么是瓶颈：** 大题占合并通过率 59–80%，当前候选在大题上零证据。常开推理和正文共用 131k 上限，撞上后三条路径都不交付。
- **证据：**
  - Lite 起草已用到 65,004 token（上限的 49.6%），推理最高 54,501。
  - 大题需求是 BookStack 的 2.9–3.5 倍，正文约 2.8 万–4.1 万 token。
  - 三条不交付路径：`main.py:281-282`、`1095-1097`（被单测锁定）、`94-97`/`1099-1100`。
  - flash 在同一链路上实际 0 交付过（`progress.md:111-114`）。
- **最小改法方向：**
  - 先用冻结的 v24 在公开 12306 需求上本地真实生成一次，测出推理与正文 token 曲线。需求在 `~/projects/volo-factory/runs/2026-09-20-goal/r28-req-12306/requirements.yaml`；约 5–10 CNY，需要你授权。
  - 把三条截断路径改成：交付已完整的文件，用剩余调用接着写缺的部分。

### 瓶颈 2：没有「每个路由真的渲染了对应实体」的通用不变量

- **为什么是瓶颈：** 这类错误不抛异常，一出现就连带掉 60–85% 的用例；自检照样报 0 问题，修复循环根本不会被触发。
- **证据：**
  - 官方 v24 自检 0 问题、官方 9/34；两行路由修正后 30/34。本地复跑两份产物，分别报 0 条和 6 条问题。
  - 同类错误有 4 次记录，7 局 Kimi BookStack 里 2 局因此掉到 9/34。
  - 09-18 已提出检查设想，一直未实现（`progress.md:275-277, 372-374`）。
- **最小改法方向：**
  - 在现有 Chromium 探针里加一步：凡是名字等于种子或引号实体名的链接，逐个点击，要求主标题包含该名字，且页面不出现「not found」。
  - 加一条静态检查：屏幕函数定义了却从未被引用。
  - 让脚手架对未知路由显式报错，不再静默回首页。
  - 用已记录的 4 份坏产物和现有满分产物做正反校准。

### 瓶颈 3：探针对 Lite 措辞过拟合，隐藏题上几乎失明

- **为什么是瓶颈：** v12 以来的主要投入不会迁移到隐藏题。隐藏题的修复循环只剩崩溃类信号；抽不到契约时，Chromium 探针整个不跑。
- **证据：**
  - 四份 Web 需求只触发 `roles`（12306 另有 `home`）。
  - 探针 21 个检查点里 15 个依赖 Lite 句式。
  - `main.py:758-760` 在抽不到契约时提前返回。
  - v24 唯一的改动是 BookStack 专属检查。
- **最小改法方向：**
  - 停止新增 Lite 句式契约。
  - 改用每份需求都有的结构：ATOMIC 场景里 WHEN/THEN 引用的名字，在可达屏幕上按渲染结果核对，而不是按源码文本核对。
  - 去掉「无契约就不跑浏览器」的提前返回。
  - 每次改探针，至少在一份本地已有的非 Lite 产物上核对误报（12306、Ctrip、SO bundle 都在）。

### 瓶颈 4：修复验收按问题条数判定，既误收也误拒

- **为什么是瓶颈：** 修复会整份重写 app.js，验收只比较探针能看见的问题条数；页面变得可达后条数上升，好的修复反而被拒。
- **证据：**
  - 误收：v4 BookStack 从 28/34 降到 23/34。
  - 误拒：v12 Keep 交付 25/32（修复本身能到 32/32）；r26b BookStack 交付 9/34。
  - 推演：同时修好 v24 路由的修复，会因 6 条多于 2 条被拒。
  - 验收时不复跑静态门禁（`main.py:1484-1513`）。
- **最小改法方向：**
  - 验收改成：本轮针对的问题消失，且修前已渲染出来的屏幕标题和引号名字一个都没少。
  - 新变得可达的屏幕上的问题，不计入拒收理由。
  - 验收时复跑静态门禁。

### 瓶颈 5：温度 1.0 的单样本方差大，没有针对灾难性失败的条件重抽

- **为什么是瓶颈：** 同一候选、同一题，独立生成的分数波动极大，一局官方试跑基本是抽签。开发决策也建立在每版一两个样本上，改进和噪声分不开。
- **证据：**

- **最小改法方向：**

  - 候选之间的取舍，改为每题至少两次独立生成后再比较。
