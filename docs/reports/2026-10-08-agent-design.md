# 2026-10-08 VOLO 决赛 agent 设计说明（初稿）

初稿写于 2026-10-07 上午，在决赛截止（2026-10-08 18:00）之前。文中的 run id、提交号、榜位和费用都是标注时刻的读数，不是终局；终局数字统一用【待截止后填写：……】占位。代码位置指 main `ad1b2f3` 上的行号。读者是上台讲这个设计的人，第 9 节是演讲提纲。

## 0. 一句话

VOLO 的决赛 agent 只读需求，在初赛产物上做增量升级：一次模型调用起草改动，再让模型只看需求写一套浏览器验收测试，然后在两道确定性检查的保护下跑一个有上限的修复环，最后只把内容变了的文件写回输出目录。

它不是多轮自由探索的工具型 agent。改动留不留、什么时候停，都由代码按固定规则判定；模型只负责写代码和写测试。

结果：【待截止后填写：最终名次、最终提交 id、两题成绩与费用、S】。

## 1. 赛题约束与这个形状的理由

**约束**（决赛须知与平台事实，见 `docs/reference/finals-roadmap.md` 第 2 节）：

- 输入只有 `requirements.yaml` 和可能为空的 `prerequisites.md`。平台在执行前把初赛选中的产物注入输出目录；agent 只能增量修改，不得清空或覆盖整个输出目录，不得探测未公开的测试。
- 测试隐藏。两题共 60 条，测试包不公开；每次运行结束后，下载包里有这次运行的官方 Playwright 报告。
- 起点是我们初赛的 GitHub 79 分产物（run `afc04ffe5b63`）和 Sheet 87 分产物（run `defb678bf0a1`），平台下发的基线与本地副本逐字节一致。
- GitHub 给的是整棵原始需求树：52 个 ATOMIC，42 个原样、5 个改动、5 个新增，约 19 万字节。Sheet 只给 10 个受测需求。受测需求各 3 个场景。需求里没有 `change_type` 字段，改动写成「Original」和「Modified」两段描述。
- 计分：S = p / (b / 0.24p)^0.1（我们所在的奖励区），p 是两题合计通过率（百分数），b 是两题被选中运行的费用（元）。榜上每队取最新一次有效提交，每题取该提交内最好的一次运行。

**为什么是一次起草加修复环**，理由有四条：

1. **唯一可靠的信号是需求本身。** 每条 ATOMIC 需求都带 GIVEN/WHEN/THEN 场景，控件名和角色写得很明确（初赛路线图第 2 节）。agent 最有价值的动作，是把需求变成可执行的检查，再用检查决定改动的去留。自由探索的 agent 拿到的也是同一份需求，多出来的只是行动自由，而没有裁判时行动自由没有方向。09-22 我们在同样两份 Ctrip 草稿上把 mini-SWE-agent 的原生工具和固定反馈修复做过对比：mini-SWE 分别用了 22 次和 17 次调用，一行代码没改，检查停在 5/9 和 6/9；固定反馈修复两份都到 9/9（`docs/reports/2026-09-23-harness-review-appendix-2-experiment-history.md` 第 3.5 节）。
2. **进化题的主要风险是把旧东西弄坏。** 每次改动都要能整体换回、能在同一套检查下前后对比。固定的检查集合加「接受或换回」规则，比开放式的多步编辑更容易守住这条线。
3. **费用进分数，但只占 0.1 次方。** 值得为通过率花钱，但每一笔都要有上限。有界的修复环让单次运行的费用可预测（第 6 节）。
4. **平台和网关的物理条件。** 运行器 1 核 CPU、2 GB（初赛规则）；网关单流约 1200 秒会被切断，偶尔整体退化（第 7 节）。一次长调用起草、之后用小改动修复，配合续写和「永远交付最后一个完整版本」，对这些条件更稳。

反过来，去掉写测试和修复也试过：初赛 09-28 只起草、不写测试不修复，两题各 6 份，24 个组合里最高 S 40.5，没有一个超过当时的正式成绩 57.4；写测试加修复在 Sheet 上值 25 到 40 条（初赛路线图「撤回：只起草」）。

## 2. 链路

### 2.1 入口与升级模式

平台把旧应用放进输出目录，入口发现目录非空就把它当模板原地升级（`oneshot/main.py:2625-2628`）。源码快照有界读取，最多 256 个文件、2 MiB，超限明确失败而不截断（`main.py:80-83`、`:1165-1194`）；点开头的路径、`node_modules`、`dist` 和根目录的 `requirements/` 不进快照（`:1158-1162`），暂存目录只由这份快照建出（`:1403-1408`）。

### 2.2 起草

起草请求依次放方言卡（`oneshot/dialect.md`）、交付契约、种子清单、需求原文，最后是旧应用源码的 JSON（`main.py:1365-1378`）。升级说明要求保留已有功能、路由、标签和资源；需求写明的位置、角色、名称或消息与旧应用不符时，按需求改旧应用；只输出改动或新增的完整文件（`:1197-1214`）。

默认模型 deepseek-v4-flash（`:37`），温度 0（`:375`）。起草最多 4 次完成调用，用于首稿、截断后的续写和空回复重发（`:44`、`:1279-1362`）；流在完整文件块之后断掉时，保留这些块按截断续写（`:473-479`）。一个文件都没改的升级算失败（`:1422-1423`）。

### 2.3 按需求自写验收测试

起草完整之后才开始写测试，避免给交付不出来的应用花测试的钱（`main.py:1424-1431`），修复阶段最多等它 3600 秒（`:59`）。

- **只看需求。** 写测试的模型看不到应用（`oneshot/testgen.py:49-51`）。按顶层需求分组，一组一个文件、最多 30 个场景，串行写（`:35-36`、`:155-172`），每个场景一条测试，标题带场景编号（`:124`）。
- **定位来自需求。** 优先角色、标签和可见文字；需求写明区域就先限定到该地标；「top」控件在页头找，单独的「global」不推出页头；加进单元格的控件在单元格里找；需求同时给出角色和文字的消息按精确名称找（`testgen.py:77-96`）。
- **守卫抽出的需求位置也交给写测试的模型**，以「在某地标内按角色和精确名称定位」的写法附在请求里（`testgen.py:181-190`）。这是 10-07 的教训，见第 3.3 节。
- **结果分三种。** pass、fail、error。测试自己的代码抛错、用了需求里没有的名字、GIVEN 造不出来而跳过，都记 error（`testgen.py:914-954`）；error 不驱动修复，也不算得失（`:8-13`）。多条测试卡在同一个 helper 行、报同一个错，合并成一条 `helper:` 发现（`:1061-1083`）。
- **测试自身的错误回写一次。** 第一次在能运行的应用上跑出自身错误的文件，带着报错让写测试的模型改一次；改写必须保留全部测试编号、不新增 skip、`expect(` 不减少，否则保留原文件（`testgen.py:731-737`，`main.py:1906-1939`）。
- 整套测试一条都判不了应用时，退回需求场景自检（`main.py:2348-2357`）。

### 2.4 修复环

修复环在 `repair_delivery`（`main.py:2338`）和 `judge`（`main.py:2164`）里。下表是全部规则。

### 2.5 交付

只回写内容变化的应用文件：先在目标旁写临时文件，全部写完再逐个改名（`main.py:1232-1255`）。任何异常之后，只要暂存目录通过交付检查，就交付最后一个完整版本并在日志里说明（`:1445-1454`）；没有一个交付文件来自模型时退出码为 1（`:2637-2641`）。真实提示、回复、用量和耗时都打进日志，密钥替换掉（`:2647-2654`）。

## 3. 两道确定性检查

两道检查都不调用模型（`oneshot/regression_guard.py:1-5`），它们在修复环里的作用是否决和驱动，不是打分。

### 3.1 旧行为守卫

- **观测。** 在隔离副本上起后端，Chromium 以未登录状态、新浏览器上下文打开首页，沿安全导航最多走 3 层、60 屏、80 秒，记录每屏可见的有名控件：角色、可访问名、所在地标（`regression_guard.py:26-28`、`:326-391`）。探针只放行同源的 GET/HEAD 请求（`oneshot/regression_probe.cjs:182`）。
- **基线。** 起草开始前复制一份不可变的起点，在后台线程里观测两遍，和起草的模型调用重叠；两遍都出现的项才进基线（`regression_guard.py:394-414`、`:40-53`）。初赛 GitHub 产物的基线 1194 项、60 屏、约 40 秒；Sheet 产物 29 项、约 2 秒（`2026-10-06-regression-guard.md` 第 1 节）。
- **对比。** 起草后、每次可运行的修复后都按基线路径重放，基线项不在了就报缺失（`:420-426`、`:228-278`）。大小写、空白、链接与按钮互换不算丢（`:100-107`）。
- **需求改动的豁免。** 需求写明改名、删除或替换，或改动需求提到该名称、所在容器或导航步骤时不报；需求点名的新名称、同一目的地的改名、选择器里保留的选项、日期基准的改变也豁免（`:64-139`）。决赛需求没有 `change_type`，豁免只剩措辞这一条入口。
- **效果。** 合成破坏 8 处全部检出，新增控件 2 处没有误报；练习赛 6 题的升级产物上报出 134 条，人工分类 132 条是真实的可见界面回归、2 条噪声（同上报告第 2、3 节）。平台试跑（提交 `b8043c3da0dd`，10-06）在 12306、BookStack、PrestaShop 上分别找回 45、24、161 项旧界面（例如改名的侧栏入口、页面上消失的 Edit/Favorite、匿名的「My account」入口）。
- **豁免严一些反而更差。** 只认逐项证据的严格版在练习平台 36/38（提交 `9fcea15aefde`，10-06）：它把需求合法去掉的「Matching notes」逼了回来，在另一题上驱动修复空转 13 轮。宽松版 38/38（提交 `9b6dfbecf17a`），采用宽松版。

### 3.2 需求位置核对

- **抽取。** 只认两种明确句式：「名为 X 的某角色控件 in the main content / header / sidebar / footer / top navigation」，以及「the top … control has <role> role and accessible name X」；后者的「top」指每页共有的页头（`regression_guard.py:142-191`）。单独的「global」只决定要核对哪些页，不决定区域（`:189`）。
- **核对。** 探针记录每个控件所在的地标（`regression_probe.cjs:59-63`）；起始页核对一般声明，「每页」的声明在所有已观测页核对（`regression_guard.py:201-225`）。
- **接入。** 没做到的位置进守卫缺失项交给修复；做到的成为保留项，之后被改掉会触发否决 2。
- **范围。** 决赛 GitHub 上抽到 2 条：正文里的「Sign in」链接、页头里的「Search」搜索框。决赛 Sheet 和练习 6 题都抽不到，这些题的提示和检查不变（finals-roadmap 第 4.5 节）。
- **为什么需要它。** 只靠提示时，起草有随机性：10-06 本地一个 GitHub 样本补上了正文登录，却漏了页头搜索，12 条测试卡在这一步（finals-roadmap F3 区域候选读数）。

### 3.3 教训：确定性检查必须和自写测试对齐

10-07 早上，审查清理后的包（提交 `75e1e32ba125`）在官方 GitHub 首个样本只拿到 15/30（run `c1cc732054e3`，3.034 元，3627 秒），其中 12 条失败是页头没有「Search」。过程是这样的：

1. 起草把全局搜索留在了首页正文里。
2. 位置核对按需求「The top global search control」报缺，但当时的修复提示写着「保留其他有用的入口」（`git show 5c24eb4` 可见旧文案），修复就在页头加了一份。
3. 自写测试在整页范围按名称找「Search」，两份同名控件让 31 条测试报歧义。按 3:1 规则，这些修复的丢失远多于获得，4 轮全被否决。

守卫要求的东西，恰好是测试惩罚的东西，修复环被两个裁判来回拉扯。修正（`5c24eb4`）有两处：守卫提示改成「同一动作的控件挪过去，不复制；用途不同的控件留在原处」（`regression_guard.py:223-225`）；写测试的模型拿到守卫抽出的需求位置，按地标定位（`testgen.py:181-190`）。换包前写死的判据是第三版代理上 GitHub 两个样本都正常退出、页头搜索在位、各不低于 22，Sheet 一个样本不低于 25；结果 GitHub 22、23，Sheet 29。新提交 `3dcb23f5c62e` 的官方 GitHub 首个样本（run `d3dd63a5feb1`，10-07 09:17 读数 19/30）页头搜索已在，3 轮修复被接受。

同一类冲突此前出现过两次：10-06 深夜守卫遇到首页两个同名同目标链接，探针不肯选，屏幕记为观测不到，于是按否决 3 拒掉了 4 轮修复（内部测试已到 125/127）；同一晚一个本地 Sheet 样本的自写测试把「Data」菜单当 menuitem 找，修复在原按钮旁加了同名控件，代理按官方的严格单匹配判它失败，样本只得 11/30。

可以讲的原则：**凡是能否决或驱动修复的确定性检查，都必须和判定得失的测试共用同一个定义**（同一个位置、同一个可访问名、同一种「一个入口」的口径），否则修复环会在两个裁判之间空转。

## 4. 证据晋升

一个改动从想法到上正式提交，要依次过四层证据：单元测试证明机制、本地校准代理比较候选、练习平台回归、官方读数。判据在动手前写死；单样本只能分辨大差异；本地分和官方分分开记（finals-roadmap 第 4 节，沿用初赛路线图第 7 节）。

**官方报告。** 每次正式运行的下载包里有官方 Playwright 报告，带逐条报错和失败测试的代码片段（finals-roadmap「F2-real」一节）。这是唯一的官方逐条信号。我们用它找原因，但不把它的断言直接变成产品规则（第 5 节）。

**按官方报告校准的本地代理。** 由另一个模型会话（Codex）按官方写法，给决赛每题 30 个场景各写一条测试，并手写参考实现证明可过（两题各两次 30/30）。代理和改进工作隔离，不进入任何改进任务的输入。第一版比官方宽：同一个包本地 GitHub 24/30，官方只有 3/30。之后按官方报告里可见的测试代码校准：第二版在两份官方产物上 60/60 逐条复现官方结果；第三版用五次官方报告校准，在 10 份官方产物上 300 条里 292 条逐条一致，本地 GitHub 读数从 28 降到 21–23，与官方对齐（finals-roadmap 决策表 10-07、迭代日志第 9 版）。练习赛的官方测试包可以下载，在本地官方镜像里复现：练习回归里 Ctrip 两条失败在本地跑 3 次、官方重跑 2 次（run `77ac453e863f`、`f6c099e53c0b`）都不复现，按偶发处理。

**消融。** 一次只改一个机制，配对比较：

| 比较 | 样本 | 结果 | 去留 |
|---|---|---|---|
| 升级时跳过源码审查 | 代理两题 | 通过数 29/30、30/30 不变；估算费用 0.78/0.64 元，此前 1.31–1.67 元；耗时约 10 分钟，此前 18–25 分钟 | 跳过（PR #127） |
| 守卫豁免严格版 | 练习平台 6 题 | 36/38，宽松版 38/38 | 用宽松版 |
| 起草改为定点编辑 | 练习平台 6 题；本地 GitHub 2 样本 | 33/38；本地两次退出 1 | 不采用 |
| 审查清理（`b608dfc`）、清理后加回四条默认做法（`860349e`）、清理前（`98754d2`） | 第三版代理，Sheet 3 样本、GitHub 2 样本 | Sheet 23/25/20、25/27/24、26/25/25；GitHub 17/15、24/22、21 | 用加回四条的版本 |
| 确定性编译官方 Light 句式的测试 | 公开 Light 题与决赛代理题 | 前者 35/38 场景可编，后者 0/60 | 默认关 |

**同一提交重跑取最好。** 平台每题取该提交内最好的一次运行，S 里的费用 b 只算被选中的两次运行（榜单的 `source_run_ids`），按初赛榜单数据核实过（finals-roadmap 第 4.5 节 10-07 01:00 段）。所以重跑只消耗队伍额度，不进 b，不会拉低 S。而单样本波动很大：提交 `d99dcad49dc5` 的 GitHub 四次 16、21、20、20，Sheet 六次 23 到 26；提交 `75e1e32ba125` 的 GitHub 15、20、21，Sheet 23 到 29（10-07 读数）。因此同一提交两题循环重跑，同一题同一时刻只能有一个正式运行。台上应该讲清楚：榜上成绩是多次运行里最好的一次，不是单次运行的期望值。【待截止后填写：最终提交两题各重跑多少次、选中的是哪两次 run】

**按 S 决定提交去留，不按条数。** 例如同样 4.8 元，51 条的 S 约 98.2，低于提交 `977c79cf0389` 50 条、3.636 元的 98.82（`docs/progress.md` 10-07 07:15 段）。榜上取最新有效提交，所以新提交跑不过保底时要删掉它，让保底回到最新；比当时最好成绩差的提交可直接删，是用户 10-07 02:21 的授权。

## 5. 拒绝做的事

用户 10-07 02:26 给的判据是：**没有隐藏测试，一个认真的工程师只读需求，还会不会这么做。**

按这个判据，Codex 对整个包做了一次独立审查（`docs/reports/2026-10-07-generalization-audit.md`），146 组规则分四类：

- **A（37 组）**：约束来自本次输入的明确要求。
- **B（77 组）**：即使没有评测，也有独立的可用性、可访问性、可维护性或验证价值。
- **C（26 组）**：把评测或内部定位器、源文本形式、断言方便性当作产品约束。
- **D（6 组）**：包内的任务名、成绩残留，或依赖某种任务专属命名和业务结构的规则。

C 和 D 全部删除或改写。删掉的包括：全页角色与名称唯一、一切错误都用 alert、关闭按钮一律叫 Close、「global」一律推出每页页头、把原生下拉改造成可点击 DOM、从「Favorite」「草稿」之类业务词推断初始状态的探针，以及注释里的任务名和成绩。同时修了一个真实的边界缺陷：旧代码升级时整树复制会遍历 `.arc/`（`d89d194`）。

**改了的，都能用需求原文解释：**

- 需求明写的位置。「Sign in」链接写明「in the main content」，搜索写明「The top global search control」，就放进正文和页头（`dialect.md:41-45`）。首个正式读数 GitHub 3/30 的主要原因就是没放对（第 7 节）。
- 需求写明名称的 status 或 alert 用 `aria-label` 命名。需求写「the status named X」时，X 就是它的可访问名；ARIA 不会从内容推出 alert 和 status 的名字（`dialect.md:25-27`，`09bb188`）。
- 需求说加进单元格的按钮放进单元格；单元格的显示文字已被需求规定时，按钮只带可访问名、不带可见文字（`dialect.md:46-48`）。
- **两条灰区，如实讲。** 审查把下面两条归为 C（评测耦合），主会话没有照删，而是收窄后加了回来：
  - 被拒绝的操作用 `role="alert"` 提示。审查删的是「一切错误都用 alert」；加回的只是「用户刚尝试、被应用拒绝的操作」（拒绝保存、编辑或输入），非紧急的更新仍用 status。依据是 WAI-ARIA APG 的 Alert 模式和 WCAG 4.1.3：被拒绝的操作是时间敏感的反馈（`dialect.md:21-24`）。
  - 对话框的关闭按钮在需求没有命名时叫 Close。APG Dialog 要求有可见、有可访问名的关闭控件，但不规定叫什么；英文界面里 Close 是最常见的默认名（`dialect.md:61-63`）。
  - 为什么说是灰区：这两条的来历是官方报告。决赛 Sheet 首个正式读数里，alert 角色挂了 4 条、Close 挂了 1 条（finals-roadmap「F2-real」）；没有这些失败，我们未必会写下这两条。但它们本身也是认真的工程师在没有隐藏测试时会选的可访问性默认值。消融显示它们确实影响分数：去掉 alert 的干净版，Sheet REQ-5-2-1 的三条在每个样本上都挂；加回后的版本三个样本都过（finals-roadmap 第 4.5 节消融表）。
  - 我们的处理：把规则收窄到有独立依据的范围，公开它的来历，不把「官方这么测」当作理由。

**不改的，即使官方报告里看得到：**

- GitHub REQ-5-5 场景 1 要文字「1 reaction」，REQ-4-5 要「Target branch: …」和种子描述「Evolution release」。需求没有写这些文字，照着报告补就是把答案写进产品。
- REQ-1-4 场景 2 同时显示「Inactive」和「Session revoked」撞了严格模式。需求写的是「或」，「或」不推出只能显示一个（`dialect.md:19-20`）；审查前那条「多选一只显示一个」的规则已删。
- Sheet REQ-5-1-2「Create filter」第二次点不到，是应用在已有筛选时把按钮换掉了，属于应用语义，不做通用规则。

**包内的硬约束。** 包按白名单打包（`scripts/package_oneshot.py:12`），`tests_oneshot/test_package_names.py` 扫描每个打包文件里有没有练习题名。包里没有题名、答案或任务专属分支；agent 运行时只读需求和起点应用，不读取、不探测隐藏测试。需要如实说明的是：我们在运行结束后读了自己运行的官方报告来找原因，初赛也用过主办方公开自测的失败信息；原则是官方报告只告诉我们去哪里看，改不改由上面的判据决定。

## 6. 成本

10-07 09:17 的榜单快照里，我们 46/60、2.922 元（GitHub run `d3dd63a5feb1` 1.852 元，Sheet run `09d67ced8e98` 1.070 元），S 92.15，第 1。其他队按榜上 S 反推：Orchestro 49 条约 7.6 元（S 89.73），Limitless' 47 条约 10.7 元（S 82.87）。用户转述同一快照里其他队在 7.6 到 40 元之间，40 元一端待核实。

这在 S 里值多少：提交 `977c79cf0389` 50/60、3.636 元，S 98.82；同样 50 条如果花 7.6 元，S 只有 91.8，要多过 4 条（54/60）才追得回来。

控费的设计，以代码为准：

- **便宜的默认模型。** deepseek-v4-flash 每百万 token 输入 3 元、缓存命中 0.1 元、输出 9 元；回退模型 Kimi HighSpeed 是 13、2.6、54 元（`main.py:67-69`）。初赛配对实验里 Kimi 每题费用是 flash 的 4 到 7 倍，通过率差异分不出来，按写死的判据选便宜的（初赛路线图 4.5）。回退只接管失败的那一次调用（`main.py:482-486`）；重试间隔 5 秒、30 秒，避免本机网络一抖就整局切到贵的模型（`:70-73`）。
- **调用与花费上限。** 起草完成调用 4 次（`:44`）；修复完成调用 24 次、每题修复花费 10 元，每次调用前按「已花加本次估算」判定（`:45-46`、`:306-320`）；传输失败共享 5 次（`:74`）；连续 4 轮被丢弃即停（`:47`）。网关在出字前拒绝（401/403/429）不计费、不计失败，按 15 到 240 秒等待，单次调用累计不超过 1200 秒（`:77-79`、`:463-472`）。
- **请求前缀缓存。** 写测试的各次调用把 system 提示和需求放在前面，文件名和回复格式放在最后，共享同一前缀（`testgen.py:191-193`）；初赛实测一套 Sheet 测试的输入费从不命中缓存的 2.17 元降到 0.64 元（初赛路线图 4.24）。修复环里，每轮都以起草请求和起草回复为前缀，被丢弃的回复不进对话（`main.py:2532`、`:2539-2548`），前缀轮轮相同。
- **不为不会产出的东西花钱。** 写测试等起草完整后才开始（`main.py:1424-1431`）。升级模式默认跳过源码审查（`:55-56`、`:1439`）：它在 13 次进化运行里零产出，每次 0.13 到 0.58 元，约占三到四成费用；消融后通过数不变（第 4 节）。
- **小改动修复。** 修复只许用 SEARCH/REPLACE 改已有文件（`main.py:142-150`），不整份重发大文件。
- **两道确定性检查不调用模型。**

也有不省的地方：写测试关推理时一套 Sheet 测试只要 1.0 元，但排序与隐藏分的秩相关从 0.97 掉到 0.38；降推理强度掉到 0.42。测试的质量来自推理，这两个开关都撤回了（初赛路线图 4.24 与「撤回：写测试降推理强度」）。

## 7. 失败与教训

**1. 练习首轮 8 题全部零分（10-06 中午，提交 `da8189ed3dd5`、`cba6094af823`）。** 现象：生成、自写测试、修复都完成了，最后发布时报 `template changed during generation`，退出 1。根因：平台在运行期间持续往输出目录的 `.arc/` 写日志，而原地升级在开始时给整个目录打了戳，发布前比对不一致就放弃；这条路径此前从没在平台上真正跑通过。改法：PR #121 只回写内容变化的应用文件（`main.py:1232-1255`），第二轮练习 6 题 38/38。

**2. 首个正式读数 GitHub 3/30（10-06 晚，提交 `8aac3a380e0c`，run `16e2557bcbfb`）。** 现象：27 条失败基本都卡在登录和打开仓库这两个入口步骤上（分项条数待核实），新功能代码大多写了却走不到。根因：官方的公共步骤从正文里的「Sign in」登录、从页头搜索框打开仓库，需求也写明了这两个位置；我们的「Sign in」只在页头、搜索只在首页正文，而自写测试在整页范围定位，查不出来。改法：方言卡与自写测试按需求写明的区域定位（`a424560`），再加确定性的位置核对（`9ba7fe9`）；提交 `977c79cf0389` 官方 GitHub 21/30、Sheet 29/30。

**3. 网关退化（10-06 22:00 到 23:45，提交 `0a76ab46dad8`）。** 现象：GitHub 3/30、Sheet 24/30。根因：网关短请求 29 秒、流式约每秒 40 字符，GitHub 起草在 14 万字符处断流，之后连续失败用完 5 次上限，修复一轮没跑；不是机制问题。改法：退化时不起正式运行，起跑前用一次短请求加一次 2000 token 流式探测（正常约 3 秒和 9 秒）。

**4. 菜单角色与重复链接（10-06 23:45，提交 `2c7c25f47b5d`）。** 现象：GitHub 15/30、Sheet 11/30。根因：Sheet 上，「角色没写明的控件按链接或按钮找」这条规则也套到了菜单条目上，应用把 menuitem 改成了按钮，官方按 menuitem 找；GitHub 上，首页两个同名同目标链接让守卫观测不到，4 轮修复全被否决。改法（`2bb856d`）：明确的命令菜单按 APG 菜单按钮模式测；守卫把同名同目标的链接当一个入口（`regression_probe.cjs:92-103`）。前一条规则后来在审查里被归为 C 并改写。

**5. 练习回归里 status 没有名字（10-07 早上，提交 `255c908e4672`）。** 现象：练习 6 题 33/38，5 条失败都是需求写「名叫 X 的 status/alert」。根因：产物有角色但没有可访问名；清理后的自写测试用「按角色找、再看包含文字」断言，查不出这个缺口。改法（`09bb188`）：测试按角色加精确名称定位，方言卡要求用 `aria-label` 命名；提交 `24658fb30bef` 36/38，剩下 2 条重跑不复现。

**6. 守卫第一次上平台全程没生效（10-06，提交 `b4a2a55414f5`）。** 现象：6 题 38/38，但守卫的每次观测都是「Playwright runtime is not installed」。根因：守卫基线和起草并行，跑得比安装 Playwright 的步骤早，缺运行时就静默退化成「无观测」。改法：缺运行时就自己安装（`regression_guard.py:285-323`）；第二次试跑（提交 `b8043c3da0dd`）在三道题上找回 45、24、161 项旧界面。教训是检查跑不起来必须看得见，不能等同于通过。

## 8. 局限

以下按审查报告「运行合规审查」与「对外表述的限制」两节如实列出。

- **没有 OS 级沙箱。** 生成的构建、后端和自写测试与 agent 同一用户运行，没有文件系统隔离和出站白名单；工具安装还可能访问 npm 和浏览器下载源。可以说默认设计不以组织者测试为输入，不能说技术上不可能越界。
- **守卫只看未登录状态。** 登录后的旧功能丢了看不见。10-06 一个样本起草整份重写 105 KB 的 `app.js`，丢了「Edit issue title」「Assignees」的代码，守卫没有报（finals-roadmap 第 4.5 节历史段）。
- **豁免与位置抽取都是启发式。** 豁免按「需求提到这个名字」判断，可能过宽；位置抽取只认两种句式，对否定、历史描述和场景作用域不完备。
- **自写测试和起草可能共享同一个误读**：同一个模型读同一份需求（`2026-10-02-generalization-bottlenecks.md`）。3:1 规则也可能牺牲部分新场景。
- **代理与官方仍有差异**：292/300，不是 300/300；只能按官方报告里看得到的代码校准。
- **单样本波动大**：同一提交 GitHub 15 到 21、Sheet 23 到 29，候选之间的差异要多样本才能分辨。
- **不是严格的单模型**：默认 flash，传输连续失败时该次调用回退到 Kimi。
